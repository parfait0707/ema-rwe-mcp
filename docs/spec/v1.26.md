# v1.26 追加要件：PR #81〜#98 のレビューで見つかった問題の修正

2026-11-20。v1.25 に加える。
v1.11〜v1.25 を実装した PR #81〜#98 を main（881b45b）でレビューし、仕様の保証が成り立たない経路、仕様と食い違う挙動、検査の穴を直した。ここには、変わった挙動だけを書く。先の版の本文は書き換えないので、食い違う箇所はこの版を正とする。実測は[検証記録](../validation.md) の 2026-11-20 の節。

1. **呼出元抽出の読み残しは、バッチが実際に読んだ範囲で判定する（v1.11 の 3）**：`cache_protocol_analysis(batch_offset=...)` は、バッチを保存するとき、その時点でその offset に配信した範囲（次の offset）も保存する。`coverage_complete=true` の統合は、保存済みのバッチではこの範囲をたどる。記録の無いバッチは、従来どおり最後の配信をたどる。同じ offset を別の `max_chars` で取り直しても、読んでいない節を読んだことにしない。読んだ節を読み残しと報告することもない。
2. **バッチに回答があれば、最終呼び出しは同じ `question` を渡す（v1.11 の 5）**：`coverage_complete=true` の呼び出しで、保存済みのバッチが別の質問の回答を持つとき、または `question` が無いのにバッチが回答を持つときは、何も保存せず `INVALID_INPUT` で断る。これまでは、回答がバッチと一緒に黙って消えていた。質問は文字列のまま比べるので、空白が 1 つ違っても別の質問になる。
3. **最終呼び出しは、解析を保存してから回答を保存する**：解析が `READING_CONTEXT_CHANGED` などで断られたときは、回答も保存しない。古い読み方の回答だけが残ることは無い。
4. **`force_refresh` は途中バッチも捨てる（v1.14 への追加）**：`analyze_protocol(force_refresh=true)` を `offset=0`（読み直しの開始）で呼ぶと、その研究の途中バッチをすべて消す。対象は、呼出元のバッチ、配信の記録、バッチごとの回答、サーバー側抽出の終わったバッチ。全バッチの後の仕上げ（`finalize_extraction`、`validate_evidence`）で失敗したサーバー側抽出は、これまで同じバッチを再利用して同じエラーを繰り返した。`offset` が 0 でない呼び出しはバッチを消さない。文脈圧縮の後の再開では `force_refresh` を付けない。
5. **空の最終呼び出しの「空」（v1.22 の 2）**：「渡された解析も空」は、`missing_information` を除いて空であることを指す（保存済みの解析と同じ扱い）。`missing_information` だけを持つ繰り返しの最終呼び出しも、保存済みの解析を置き換えずに `INCOMPLETE_EXTRACTION` で断る。
6. **データソース名の照合は、項目と文の区切りをまたがない（v1.12 の 3）**：
   - 名前の 2 語の間に `;` があれば、つながりとしない。
   - 間に他の語が入るときは、その間に文末（`.`、`!`、`?` の後に空白か終わり）か名前自身の語があれば、つながりとしない。`Hospital admissions; Episode counts; Statistics Denmark` は `Hospital Episode Statistics` に一致しない。`the Danish National Prescription Registry and Patient Registry` は `Danish National Patient Registry` に一致しない。
   - 隣り合う 2 語の間の点（`U.S. Medicare`）と、略語の括弧（`Clinical Practice Research Datalink (CPRD) GOLD`）は、これまでどおり通る。
7. **名前の引用を足す条件（v1.12 の 4）**：
   - 名前の周りの切り出しが引用の上限（1,000 文字）を超えるときは足さない。結果は通常の `EVIDENCE_INVALID` になる。これまでは、検証の外の例外（`ValidationError`）で終わった。
   - 探すページの近さは、事実が引用したどのページからも測り、最も近いものを使う。これまでは、最初に引用したページからだけ測っていた。
   - 引用が 8 件あり、名前が方法の本文にはある事実の `EVIDENCE_INVALID` は、そのことを述べる。8 件の事実には名前の引用を足さないので、1 件減らすか、名前のある箇所を引用する。これまでは「本文にも無い」と述べていた。
8. **`server` の印は、サーバーが付けたものだけにする（v1.13 の 2）**：呼出元が `cache_protocol_analysis` と `cache_protocol_answer` に渡した引用の `server` と、内部 LLM が返した引用の `server` は、サーバーの処理（ページの訂正、名前の引用の追加、検証）の前に消す。保存される印は、そのサーバーが付けたものだけになる。比較表の「名前の記載 p.」も、サーバーが足した引用だけを数える。
9. **`research_protocol` の `force` と、終わった探索（v1.15 の 2、3、5）**：
   - 探索が終わり、その結果をまだ誰も受け取っていなければ、次の呼び出しは `force` の有無に関係なく、その結果を受け取る。回答は `cached=true` で返り、`exploration_limit_reached` とエラーもそのまま返る。`status=answering` の後は、`force=true` を含む同じ引数で呼び直せば結果が届く。これまでは、`force=true` の呼び直しが結果を捨てて新しい探索を始めた。
   - 探索が動いている間は、`force` の無い呼び出しも、保存済みの古い回答ではなく、その探索に合流する。
   - `force=true` が新しい探索を始めるのは、探索が動いておらず、受け取られていない結果も無いときだけ。
   - 探索の中の PDF の解析、検索、読み取り、引用の検証、保存は、イベントループの外のスレッドで行う。待っている呼び出しの `LLM_WAIT_SECONDS` と、他のツール呼び出しが、PDF の処理で遅れない。
10. **注釈と進捗通知（v1.16 の 2、3、4）**：
    - `cache_heading_translations` を破壊的（`destructiveHint=true`）にする。英訳を写しを残さずに置き換え、英訳が変わればその研究の途中バッチを消すため。読み取り専用（いいえ）、冪等（はい）、外部通信（いいえ）は変えない。v1.16 の 3 の「見出しの英訳の変更は破壊的としない」は、解析の履歴だけを見ていた。
    - `compare_protocols` は、全研究のプロトコルを取得した後に、最後の進捗 `(n, n)`（`Retrieved every protocol`）を送る。
    - 進捗通知の送信に失敗しても（クライアントの切断など）、ツールは処理を続ける。失敗は stderr に warning として記録する。
11. **計測の記録（v1.12 の 5）**：例外で終わったツール呼び出しも `tool=` の行を記録する。そのときの `status` は例外の型の名前で、`chars=0`。
12. **カタログのスナップショットの取り込み（v1.18）**：
    - 起動時の確認は、デーモンスレッドで動く。サーバーの終了はその終わりを待たない。これまでは、クライアントが閉じても、取得と置き換えが終わるまでプロセスが残った。途中で止まっても、置き換えは 1 つのトランザクションなので、カタログは元のまま。
    - 作業フォルダは、DB と同じフォルダの `ema-rwe-update-*` とする。止まった更新が残したものは、次の更新の開始時に消す。対象は、フォルダ自身と直下のファイルの最新の更新時刻が 6 時間より古いものだけ。取得中のファイルは更新時刻が進むので消さない。消せないときは stderr に warning を記録し、更新は続ける。
    - 転送は 1 回ずつたどり、要求を出す前に転送先が GitHub の中（HTTPS）かを確かめる。転送は 5 回まで。GitHub の外へは要求を出さない。これまでは、転送をたどった後に確かめていた。
    - 手元の DB の最後の CSV の取り込みが manifest の `created_at` 以降なら、本体を取得せずに `kept_local_import` とする。取得の後の比較も残す。
    - manifest の `snapshot_id` は `YYYYMMDD` の形でなければ `invalid_snapshot` とする。展開した DB の日付（取り込んだエクスポートのファイル名の日付の最大）が `snapshot_id` と違うときも `invalid_snapshot` とする。手で渡す `--file`／`--manifest` にも、GitHub からの取得にも当てはまる。
    - 展開は、manifest の `database.size`（上限 4 GiB）を超えたところで止め、展開先を消して `invalid_snapshot` とする。`scripts/build_catalogue_snapshot.py --verify` も同じ上限で拒否する。
    - カタログの表の置き換え（`refresh_from_bundle`。同梱 DB による差し替えとスナップショットの取り込みの両方）が失敗したときは、理由を stderr に warning として記録する。カタログは元のままで、結果は従来どおり（取り込みでは `not_applied`）。
13. **`EMA_CATALOGUE_UPDATE=off` は、アプリの新しい版も知らせない（v1.19 の 6）**：off のときは、以前の確認の記録が残っていても、`ema-rwe update-catalogue` を手で実行した後でも、`app_update_available` を出さない。
14. **名前だけの短い節の隣（v1.23 の 3）**：
    - 「その見出しの節の合計」は、同じ見出しが続く連続したチャンク（その節の全ページ）の文字数の合計とする。質問に一致したページだけでは数えない。離れた場所にある同じ見出し（要旨と本文の「Outcomes」など）は、別の節とする。
    - 隣の節は、親の下の兄弟の節と、その下位の節に限る。親の節そのもの（`9.3.2` に対する `9.3`）と、もとの節の下位の節（`9.3.2.1`）は含めない。
    - 背景・参考文献などの役割の節は、隣の節としても持ち上げない。
15. **統合での由来の記録（v1.23 の 1、2）**：統合で初めて受け取った入れ子のブロック（`cohort` など）でも、どの深さのリスト（`cohort.design_schema.time_windows` など）の項目にもバッチの由来を記録する。上限を超えたリストを各バッチから順に採る規則は、2 段目のリストにも当てはまる。初めて受け取ったブロックの中でも、同じことを言う項目をまとめる。
16. **正解データによる検査（v1.20、v1.24。スクリプトと正解データだけ）**：
    - `scripts/extraction_eval.py check` の質問への検索は、`research_protocol` と同じ件数（`exploration.RESEARCH_LIMIT`、30）、同じ予算（`EMA_RESEARCH_BUDGET_CHARS`）、同じ数え方（`exploration.within_budget`。予算を超えたヒットだけを省き、後ろの短いヒットは入れる）、空白を詰めた後の本文で行う。これまでは、件数と予算 40,000 を写し、予算を超えた最初のヒットで止めていた。
    - 値（`values`）の照合では、一致の左が英数字の境界であることを求める。数字で始まる一致は、右にも数字が続かないことを求める（`3` は `13` に、`18` は `2018` と `180` に当たらない）。コードは下位コードにも当たる（`C25` は `C25.1` と `C251` に、`GFEA` は `GFEA001` に当たる）。`check` の値のページの確認と、`grade` の `correct` の両方に使う。研究 105807 の O2（生存率の年数）の値は `\b1\b\D{0,12}\b2\b\D{0,12}\b3\b` とする。
    - `grade` は、開いたサービスを閉じる。
17. **開発の検査（`scripts/check.py` と pre-push hook）**：
    - pre-push hook は、ブランチの削除だけの push では検査を走らせない。PR #85 で入れたときから、この判定は働いていなかった。入力が空の push では、従来どおり走らせる。
    - スクリプトは `uv run scripts/<名前>.py` の形で起動する（`.claude/rules/package-management.md`）。`check.py` の `gold` の段階と hook も、この形で起動する。
    - `check.py` は、コマンドが見つからないときと wheel が作られなかったときも、traceback ではなく、失敗した段階の名前を出して終わる。
18. **`analyze_protocol` を破壊的にする（v1.16 の 3 への追加、リリース前監査）**：`analyze_protocol` の `destructiveHint` を true にする。`force_refresh=true` を `offset=0` で呼ぶと、その研究の途中バッチとバッチごとの回答を写しを残さずに消すため（この節の 4）。置き換えた解析は従来どおり履歴に残る。読み取り専用（いいえ）、冪等（いいえ）、外部通信（はい）は変えない。破壊的なツールは 6 つになる。
19. **CLI の `analyze` はサーバー側抽出の終わりまで待つ（v1.15 の `ask` と同じ）**：`Service.analyze_protocol` に `poll`（既定 true）を足す。`poll=false` は `LLM_WAIT_SECONDS` を超えても `status=extracting` を返さず、抽出が終わるまで待つ。CLI は呼び出しごとに別のプロセスで、終わるとサーバー側抽出のタスクも止まるので、CLI の `analyze` は `poll=false` で呼ぶ。MCP の `analyze_protocol` は従来どおり待機の後に `status=extracting` を返す（MCP の引数は増やさない）。
20. **`cache_heading_translations` は読み方が変わったかを返す**：応答に `reading_changed`（真偽値。保存した英訳が前と違う（初めての保存を含む）とき true。このとき、その研究の途中バッチ、バッチごとの回答、動いているサーバー側抽出があれば捨てる）を足す。true のとき、`instruction` は抽出のバッチを `offset=0` から読み直すよう伝える。
21. **変えないもの**：ツールの数と引数、抽出のスキーマとその版、fingerprint、MCP の `instructions`、`source_assessments` の上限（120。先頭から）。
