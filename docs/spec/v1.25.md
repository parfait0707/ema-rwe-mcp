# v1.25 追加要件：質問別回答の上限と、バッチごとの回答の統合

2026-11-20。v1.24 に加える。
値を照合する採点（v1.24）で、抽出と同時に質問に答えた回（`analyze_protocol` に `question` を付ける既定の経路）が、付録のコードと別の章の値を落とすことが分かった。原因は、バッチごとの回答を統合するときに「最初の 30 件」だけを残していたこと。4 つの研究で 34〜57 件の回答が見つかり、最後のバッチ（付録）の分が落ちていた。実測は[検証記録](../validation.md) の 2026-11-20 の節。

1. **質問別回答の上限を 60 件にする**：`ProtocolAnswer.answers` の上限を 30 から 60 に上げる。`cache_protocol_answer`、`cache_protocol_analysis` の `answer`、`research_protocol` の回答、`answer_schema` のすべてに当てはまる。保存済みの回答（30 件以下）は、そのまま読める。抽出のスキーマ（`Extraction`）、その版、fingerprint、抽出の指示は変えない。
2. **バッチごとの回答は、同じものをまとめ、各バッチから順に採る**：呼出元抽出の `coverage_complete` での統合と、内部 LLM の全文の回答の統合の両方で、
   - 値が同じ回答（大文字と小文字、空白、記号の違いを除く）は、根拠を合わせて 1 つにする（8 件まで）。
   - それでも 60 件を超えるときは、最初の 60 件ではなく、バッチごとに 1 件ずつ順に採る（並びは元のまま）。`missing_information` の先頭に、件数と採り方を書く（`78 verified answers found; only 60 are kept (schema limit), 18 omitted, taken in turn from the 4 batches.`）。
3. **保存のときの検証**：回答の根拠は、20 件ずつ、全件を検証する（これまでの検証は、41 件以上の回答を受け付けなかった。上限 30 では起きなかった）。
4. **変えないもの**：`source_assessments` の上限（120。先頭から）と、バッチごとの回答の求め方。
