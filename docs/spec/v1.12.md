# v1.12 追加要件：解析済み PDF の再利用、読み手に渡す本文の空白、データソース名の確認、ツール呼び出しの計測

2026-11-19。v1.11 に加える。
根拠は、4 件の実プロトコルでの計測と、方式の比較で見た検証エラーの内容（[検証記録](../validation.md) の 2026-11-19 の節）。

1. **同じ PDF は 1 プロセスで 1 回だけ解析する**：`extract_pages` は、PDF のバイト列の SHA-256、parser の版、しおりを使うかどうか、読み方（見出しの英訳）を鍵に、解析したページをプロセスのメモリに保つ（新しい順に 8 件）。同じ鍵への同時の要求は 1 回の解析にまとめる。解析に失敗した結果は保たない。`sections` の結果もページに付けて保ち、呼び出しごとに複製を返す（呼出側が節に項目を足したり本文を外したりするため）。キャッシュはメモリだけで、プロセスをまたがない（CLI は呼び出しごとに 1 回は解析する）。解析結果そのものは変えないので、fingerprint と保存済みの解析はそのまま有効である。
2. **読み手に渡す節の本文は、3 つ以上続く空白を 2 つに詰める**：対象は `analyze_protocol` のバッチ、`search_protocol_text`、`read_protocol_text`、`research_protocol` の応答、内部 LLM へ送る本文。表の列や両端揃えが PDF に残す空白で、読む量の 5〜18% を占めていた。列の切れ目が見えるように 2 つは残し、空行は変えない。バッチの大きさ（`max_chars`、`LLM_BATCH_CHARS`）は詰めた後の本文で数える。引用の照合は空白をまとめて比べるので、詰めた本文から写した引用も PDF と一致する。節の分け方、節の ID、役割の判定は、詰める前の本文で行う（parser の版は変えない）。
3. **データソース名は単語の並びで確かめる**：`data_sources` と `source_assessments` の `value` は、引用のどれかに、名前の単語がその順に書かれていれば通す。大文字と小文字、記号の違いは無視する（`CPRD-Aurum` と `CPRD Aurum` は同じ）。名前の単語の間には、ほかの単語が 3 つまで入ってよい（表では名前が行をまたぎ、別の列の値が間に入る）。単語は丸ごと一致させる（`HES` は `hesitant` に一致しない）。プロトコルに無い語を足した名前（`SDRN-EPI (Scotland)` など）は通さない。
4. **名前が引用に無く、引用したページにあれば、名前を含む引用を足す**：呼出元の引用は、使い方や定義を述べる文で、名前を見出し、表のセル、前の文に任せていることが多い。その場合、サーバーは引用済みのページから名前の書かれた箇所の前後を逐語で切り出し、その事実の引用に加えてから検証する（引用が 8 件あるときは足さない）。サーバー側抽出の修復（`prune_unverifiable`）と同じ扱いで、両方の経路が同じ規則になる。引用したどのページにも名前が無ければ `EVIDENCE_INVALID` を返し、その名前と直し方（プロトコルの書き方に合わせる、または名前のある箇所を引用する）を伝える。質問別回答の `source_assessments` も同じ。
5. **ツール呼び出しを計測して stderr に記録する**：MCP サーバーは、ツールごとに 1 行、所要時間（ms）、応答の文字数、状態（`status` かエラーコード）、その呼び出しで解析した PDF の数、再利用した数、解析に使った時間を記録する（`tool=... ms=... chars=... status=... pdf_parsed=... pdf_reused=... pdf_parse_ms=...`）。PDF を解析したときは `pdf_parse pages=... ms=...` も記録する。stdout には書かない。`scripts/time_tools.py <研究ID>...` は、LLM なしで 1 研究分のツール呼び出しを順に実行し、所要時間を表にする（DB は一時的な複製を使う）。
