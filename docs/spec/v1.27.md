# v1.27 追加要件：呼出元が保存した引用の節のラベル

2026-11-20。v1.26 に加える。
呼出元（MCP クライアント）が保存した引用の `evidence.section` が、すべて null のまま残っていた（Issue #101）。抽出と探索の指示は「`evidence.section` は null のままでよい。サーバーが導く」と伝えるが、節を導く処理は内部 LLM の経路（`prune_unverifiable`）にしか無かった。ここには、変わった挙動だけを書く。実測は[検証記録](../validation.md) の「呼出元が保存した引用の節のラベル」の節。

1. **呼出元の引用にも節のラベルを導く**：`cache_protocol_analysis` の `analysis` と `answer`、`cache_protocol_answer` の回答で、`section` が null の引用に、内部 LLM の抽出と同じ規則で導いたラベルを入れる。内部 LLM の質問別回答（`research_protocol`）も同じ保存（`Explorer.save`）を通るので、null のまま残っていたラベル（別のページへ動かした引用、データソース名を足した引用、段階探索で null だった引用）も埋まる。規則は、引用したページのチャンクのうち、引用を含み、見出しがそのページの本文に書かれている節が 1 つだけなら、その節のラベル。そのような節が無いか、2 つ以上あれば null のまま。
2. **呼出元が付けたラベルは残す**：null でないラベルは書き換えない。そのラベルは従来どおり `validate_evidence` が検査する（引用を含む、そのページの同じラベルの節があること）。サーバー側抽出（`analyze_protocol` の内部 LLM）のラベルは、従来どおり信用せず導き直す。
3. **順序**：ページの訂正（`server="page"`。動かした引用の節を消す）と、データソース名の引用の追加（`server="source_name"`）の後に導く。動かした引用は、動かした先のページの節を受け取る。導いた後に `validate_evidence` で検査して保存する。`coverage_complete` の統合でバッチの回答をまとめて保存するときも、同じ処理を通る。
4. **変えないもの**：ツールの数と引数、抽出と回答のスキーマとその版、fingerprint、`server` の印、サーバー側抽出（`prune_unverifiable`）の挙動。保存済みの解析と回答は書き換えない（次に保存したときから節が入る）。
