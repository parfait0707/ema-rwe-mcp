# v1.13 追加要件：引用のページの訂正、サーバーが手を入れた引用の印、引用の下限と上限の案内

2026-11-19。v1.12 に加える。
根拠は、v1.12 の確認で残った検証エラー（8 字に満たない引用、ページ番号の誤り、1 つの事実に引用が 9 件以上）と、サーバーが足した引用を保存した解析で見分けられなかったこと（[検証記録](../validation.md) の 2026-11-19 の節）。

1. **別のページにある逐語の引用は、そのページに直す**：呼出元が渡した引用が、示したページには無く、ほかのページに逐語であるとき、サーバーはその引用を持つ最も近いページに直してから検証する。呼出元は物理ページを数え違えることがある（次のページの先頭の文など）。検証するのは引用の文そのものである。どのページにも無い引用と、前後に同じ距離で 2 か所ある引用は直さず、従来どおり `EVIDENCE_INVALID` を返す。直した引用の `section` は外す（示したページの節の名前だったため）。解析の全項目と、質問別回答（`cache_protocol_answer`、1 回方式の `answer`）に適用する。サーバー側抽出の修復は、従来どおり前後 1 ページだけを見る。
2. **サーバーが手を入れた引用には印を付ける**：`Evidence` に `server` を加える。`source_name` は、データソース名が引用に無かったためにサーバーが足した、名前の書かれた箇所（v1.12 の 4）。その事実の使い方や定義を支える引用ではない。`page` は、サーバーがページを直した引用（上の 1）。印の無い引用は、呼出元か内部 LLM が渡したままである。サーバー側抽出の修復（`prune_unverifiable`）が足した引用と直したページにも同じ印を付ける。`server` は省略できる項目で、抽出スキーマの版（0.3）と fingerprint は変えない。保存済みの解析は、印の無い引用としてそのまま読める。
3. **比較表は、名前の箇所のページを分けて示す**：「PDF由来のタイプ・用途・判定根拠」の列のページは、`p. 48; 名前の記載 p. 47` のように、定義を述べる引用のページと、サーバーが足した名前の箇所のページを分ける。
4. **引用の下限と上限を、読む場所に書く**：`analyze_protocol` の指示と抽出スキーマの説明に、引用は 8 字以上（コードや単語だけのときは、その行ごと引用する）、1 つの事実の引用は 8 件まで（それ以上は事実を分ける）と書く。スキーマには以前から `minLength` と `maxItems` があったが、呼出元は繰り返し違反していた。下限と上限そのものは変えない。抽出の指示の本体（`EXTRACTION_PROMPT`）は fingerprint に含まれるので変えず、バッチの読み方の説明に加える。
