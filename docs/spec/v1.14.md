# v1.14 追加要件：サーバー側抽出の途中保存

2026-11-20。v1.13 に加える。
根拠は、サーバー側抽出の途中結果がプロセスのメモリにしか無く、1 バッチの失敗やサーバーの再起動で全バッチをやり直していたこと（[検証記録](../validation.md) の 2026-11-20 の節）。

1. **終わったバッチは DB に保存する**：サーバー側抽出（内部 LLM を設定した `analyze_protocol`）は、プロバイダが返して抽出スキーマの検証に通ったバッチを、その都度 `extraction_batches` に保存する（種別 `provider`、鍵は研究、fingerprint、読み方、バッチの番号）。呼出元抽出の途中バッチ（v1.11）と同じ表で、カタログの差し替えやスキーマの版には関わらない。
2. **再開では、足りないバッチだけを問い合わせる**：次の `analyze_protocol` は、保存済みのバッチを読み、残りだけをプロバイダへ送ってから統合する。対象は、1 バッチの失敗（プロバイダの障害、スキーマに合わない応答）の後のやり直しと、サーバーの再起動の後の呼び出しの両方。進行中のタスクそのものは従来どおりメモリにあり、再起動で失われるが、終わった分は失われない。
3. **同じ本文のバッチだけを再利用する**：保存したバッチには、そのバッチが含んだ節の本文の署名（SHA-256）を付ける。番号が同じでも、署名が今のバッチと違えば再利用せず、抽出し直す（`LLM_BATCH_CHARS` を変えた、節の分け方が変わった場合）。PDF、モデル、プロバイダ、抽出の指示、parser が変われば fingerprint が変わり、読み方（見出しの英訳）が変われば鍵が変わるので、古いバッチは使われず、新しいバッチを保存した時点で消える。保存したバッチが今のスキーマに合わなければ、そのバッチも抽出し直す。
4. **1 バッチの失敗で、ほかのバッチを捨てない**：あるバッチが失敗しても、並行して動いているほかのバッチは最後まで実行して保存する。エラーは全バッチが終わってから返す（従来は最初の失敗で返し、ほかの結果を使わなかった）。
5. **解析を保存したら、途中バッチを消す**：統合、引用の検証、保存が済んだ時点で、その研究の途中バッチを消す。
6. **進捗は再利用した数を示す**：`status=extracting` の `progress` は `done`、`total` に加えて `reused`（保存済みで問い合わせなかったバッチの数）を持つ。`done` は再利用した分を含む。
7. **対象外**：`research_protocol` の全文一括回答（質問別のバッチ）は保存しない。見出しの英訳は 1 回の問い合わせで、従来どおり。
