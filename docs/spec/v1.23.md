# v1.23 追加要件：統合での重複のまとめと上限の扱い、名前だけの短い節の隣の節

2026-11-20。v1.22 に加える。
変更後の版での採点（[検証記録](../validation.md) の 2026-11-20 の節）で残した 2 点を直す：バッチの統合で上限に達して項目が切られること、定義が別の節にあるときに質問への最初の範囲に入らないこと。

1. **同じことを言う項目は、統合で 1 つにする**：バッチの統合（呼出元抽出の `coverage_complete`、内部 LLM のバッチの統合）で、リストの項目（`data_sources`、`source_assessments`、`outcomes`、`disease_definitions`、`key_notes`、`cohort` の基準など）は、値が同じなら 1 つにまとめる。同じとは、大文字と小文字、空白、記号の違いを除いて一致すること。`source_assessments` は、さらに役割（`role`）と種別（`types`）も同じであること。略称と正式名（CPRD と Clinical Practice Research Datalink）は、別の項目のままとする。
   - 根拠は合わせる（8 件まで）。
   - `usage` は、確かな方を採る（unclear < candidate < used < planned）。planned と used の両方があれば planned とする（プロトコルは計画であり、計画段階のデータソースを実使用と呼ばない）。
   - `source_assessments` は、どれかが explicit なら explicit、どれかが連結を要するなら要するとし、異なる `definition` は改行でつなぐ（4,000 文字まで）。
2. **上限を超えたリストは、各バッチから順に採る**：まとめた後もスキーマの上限（`key_notes` 20、`data_sources` 60 など）を超えるリストは、最初の N 件ではなく、バッチごとに 1 件ずつ順に採って N 件にする（残す項目の並びは元のまま）。これまでは、最初のバッチの項目で埋まり、後のバッチ（解析、限界）の項目が落ちていた。`missing_information` の注記は、採り方を書く（`... only 20 are kept (schema limit), 6 omitted, taken in turn from the 5 batches.`）。スキーマの上限、スキーマの版、fingerprint、抽出の指示は変えない。
3. **名前だけの短い節の隣の節を、その直後に並べる**：`search_protocol_text` と `research_protocol` で、見出しが質問の語を含み、本文が短い節（その見出しの節の合計が 1,000 文字以下）があるとき、同じ番号の親を持つ隣の節（`9.3.2` に対する `9.3.1`、`9.3.3`、`9.3.3.1`）のうち、それ自体も質問の語に一致したものを、その節の直後の順位にする（結果の行に `beside` として、もとの節の `section_id` を持つ）。「Outcomes definition」が数行でアウトカムを挙げるだけで、定義は隣の「Exposure definition」にある、という書き方への対応。番号が 3 階層以上の節だけを対象にし（章の直下の節では、隣が章の全体になる）、長い節（自分で定義を持つ）と、背景・参考文献などの節は対象にしない。
4. **正解データ**：`outcomes.json` に、研究 49285 の、曝露の定義の節に書かれたアウトカムの定義の 4 項目を加える（中止の日付、現在使用の期間と 30 日の猶予、切替えの意味、追加と切替えの 90 日での分類）。アウトカムは 31 項目、全体で 82 項目。
