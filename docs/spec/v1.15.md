# v1.15 追加要件：`research_protocol` の待機

2026-11-20。v1.14 に加える。
根拠は、内部 LLM を設定した `research_protocol` が、プロバイダの回答が出るまで 1 回の呼び出しの中で待ち続けていたこと。全文の一括回答は 2 分前後かかり、Codex のツールのタイムアウト（180 秒）に近い（[検証記録](../validation.md) の 2026-09-24 の未検証事項と 2026-11-20 の節）。

1. **プロバイダの探索は、呼び出しとは別に動かす**：内部 LLM を設定した `research_protocol` は、全文の一括回答とその後の探索ループを、サーバーのプロセスのタスクとして実行する。呼び出しは `LLM_WAIT_SECONDS`（既定 120 秒。`analyze_protocol` と共通）だけ待ち、終わっていれば結果を返す。終わっていなければ `status=answering` と、質問、読み方（`reading`）、もう一度呼ぶ旨の指示を返す。
2. **同じ質問の呼び出しは、動いている探索に合流する**：同じ PDF、質問、読み方、プロバイダ設定（回答のキャッシュの鍵が同じ）で呼ぶと、新しい探索を始めず、動いている探索の結果を待つ。`force=true` でも、動いている探索があれば合流する（二重に問い合わせない）。`force=true` が新しい探索を始めるのは、動いている探索が無いときである。
3. **結果の受け取り**：探索が回答を保存して終わっていれば、次の呼び出しは保存済みの回答を返す（`cached=true`）。保存に至らなかった結果（`exploration_limit_reached`）とエラーは、終わった後の最初の呼び出しがそのまま受け取り、その次の呼び出しは新しい探索を始める。
4. **CLI は最後まで待つ**：`ema-rwe ask` は呼び出しごとに別のプロセスなので、`status=answering` を返さず、探索が終わるまで待つ（従来どおり）。
5. **呼出元の手順**：`status=answering` を受けたら、同じ引数で `research_protocol` をもう一度呼ぶ。その間、呼出元は自分で探索しない。比較の指示と手順書にそう書く。
6. **対象外**：内部 LLM を設定していない経路（`needs_client_exploration`）は変えない。動いている探索はプロセスのメモリにあり、サーバーの再起動で失われる。全文の一括回答のバッチは保存しない（v1.14 の 7 のとおり）ので、再起動の後は最初からになる。
