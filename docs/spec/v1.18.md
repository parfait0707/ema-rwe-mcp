# v1.18 追加要件：カタログのスナップショットの取り込み

2026-11-20。v1.17 に加える。
[コードとデータを別々に版管理する実装計画](../research/202610081527_code_data_versioning_plan.md)の段階 2 と 3。根拠は、月ごとのカタログを使うのに、利用者が MCP の設定の固定タグを書き換えて再起動する必要があったこと。実測は[検証記録](../validation.md) の 2026-11-20 の節。

1. **取り込むもの**：このプロジェクトの GitHub Releases に、タグ `data-YYYYMMDD` で公開したスナップショット（`manifest.json` と `ema-catalogue-YYYYMMDD.sqlite3.gz`）。下書きとプレリリース、2 つのファイルがそろわないリリースは対象にしない。最も新しい日付のものを使う。
2. **通信先と時機**：通信先は GitHub だけで（`api.github.com`、`github.com`、転送先の `*.githubusercontent.com`。HTTPS のみ）、EMA には通信しない。検索とツールの呼び出しの中では通信しない。サーバーは起動時に、ツールの処理とは別のスレッドで 1 回だけ確かめる。前回の確認（失敗を含む）から 24 時間以内なら確かめない。
3. **サーバーが自分で更新する DB**：利用者のデータフォルダにサーバーが用意した DB だけ。`EMA_DB_PATH` で指定した DB と、チェックアウトの中の DB（Git で管理している `data/ema.sqlite3`）は、利用者のコマンドでだけ更新する（新しい版の同梱 DB による差し替えと同じ決まり）。
4. **設定**：`EMA_CATALOGUE_UPDATE` は `apply`（既定。検証に通った新しいスナップショットを取り込む）、`check`（知らせるだけ）、`off`（確かめない）。`EMA_CATALOGUE_RELEASES_URL` で、リリースの一覧の URL を変えられる（別のリポジトリから配る場合）。
5. **手動の更新**：`ema-rwe update-catalogue` は、どの DB にも使える。`--check` は知らせるだけ。`--file <.sqlite3.gz> --manifest <manifest.json>` は、手で取得したスナップショットを通信なしで取り込む（GitHub に出られない環境のため）。MCP のツールは足さない。
6. **取り込みの条件**：次のどれかに当たれば取り込まず、理由を記録する。
   - 今の DB の日付（取り込んだエクスポートのファイル名の `YYYYMMDD` の最大）が、スナップショットの日付以上である（`up_to_date`）。このときは manifest も本体も取得しない。
   - manifest の `schema_version` がこのパッケージと違う、または `min_app_version` がこのパッケージより新しい（`app_update_required`）。本体は取得しない。
   - 利用者が取り込んだ CSV の方が、スナップショットの取り込みより新しい（`kept_local_import`）。
   - manifest がリリースの日付と合わない、圧縮後か展開後の SHA-256 が manifest と違う、DB が `integrity_check` に通らない、通信が GitHub の外へ出た（`invalid_snapshot`）。
7. **差し替え**：検証に通ったスナップショットは、同梱 DB の差し替えと同じ処理（`refresh_from_bundle`）で、カタログの表だけを 1 回の書き込みトランザクションで置き換える。解析、質問別回答、読み方、保存した PDF、途中バッチ、利用者の観測は残る。取得したファイルは DB と同じフォルダの一時フォルダに置き、成否によらず消す。
8. **失敗しても動き続ける**：GitHub に届かない（`unreachable`）、要求の上限に達した（`rate_limited`）、検証に通らない場合も、例外にせず、今のカタログのまま動く。サーバーの起動時の確認は、どんな失敗でもサーバーを止めない。CLI は、失敗の結果を `CATALOGUE_UPDATE_FAILED` として返す。
9. **状態の表示**：`catalogue_status` に `catalogue_snapshot`（今の DB の日付）と `update`（`mode`、`automatic`、最後の確認の日時 `checked_at`、`result`、`reason`、`latest_snapshot`、取り込んだ場合は `applied_snapshot` と `applied_at`）を加える。記録は DB と同じフォルダの `catalogue_update.json` に置く。
10. **信頼の範囲**：SHA-256 は manifest から取り、manifest は同じリリースから取る。確かめられるのは転送と保存の途中で壊れていないことであり、公開した者の真正性ではない。信頼の根拠は、コード（`uvx --from git+https://...`）と同じ GitHub のリポジトリである。
11. **v1.17 への追加**：ツールを持たない CLI のサブコマンドに `update-catalogue` を加える。
12. **対象外（計画の段階 4 と 5）**：解析と比較表へのスナップショットの日付の記録、月ごとの DB のコミットの廃止、アプリの新しい版の通知。
