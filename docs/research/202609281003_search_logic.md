# 検索ロジックの再検討：Web 検索・RAG・医学文献検索の知見から

## 調査目的

EMA RWD カタログ（3,312 研究）から、ユーザーの研究課題に合う先行研究を探す検索ロジックを見直す。一般の Web 検索と RAG の検索技術、医学・臨床研究の検索研究を調べ、この MCP が採るべき方式を決める。

## 前提と制約（ユーザー判断、2026-09-28）

- 追加してよい要素は **呼出元 LLM（Claude Code／Codex）の活用拡大だけ**とする。ローカル埋め込みモデル、外部の埋め込み API、事前計算した索引の同梱は使わない。既定の経路に追加の API キーを必要としない。リポジトリは公開（MIT）である。
- 優先順位は **段階で両立**する。一次検索で再現率を最大化し、後段で適合率を上げる（系統的レビュー型）。

## 調査方法・参照元

- 並列の調査 2 本（opus サブエージェント）で、一次資料（論文 PDF、公式文書）を中心に読んだ。数値は各報告の出典表に URL 付きで記録してある。
  - Track A（Web 検索・RAG）：`docs/agent_report/202609281001_opus_track-a-web-rag.md`
  - Track B（医学・臨床研究の検索）：`docs/agent_report/202609281002_opus_track-b-biomedical.md`
  - どちらも Git 管理外の中間成果物で、本文書が恒久版である。
- 未確認の事項：
  - blog.google に接続できず、BERT・MUM・スペル補正・パッセージランキングの数値は検索結果の抜粋だけで確認した。
  - TREC CT 2022／2023 の総括論文は取得できなかった（404）。
- 手元の実測（同梱カタログ HEAD 版）で、項目ごとの充足率を測った。
  - 目的 98%、説明 90%、Outcomes 81%、Medicinal condition 80%、INN/ATC 78%、データソース名 41%。
  - Outcomes が空の研究が 19% あり、`role=outcome` はこれらをタイトルと目的だけで探している。

## 主な発見

1. **LLM が生成した多数の短い検索語を個別に検索し、結果を統合するのが最も効果が大きい。**
   - TrialGPT：患者記録をそのまま検索すると Recall@500 が 50.0%、GPT-4 が生成したキーワードごとに BM25 で検索して統合すると 86.2% になった。
   - Neural Query Synthesis：TREC CT 2021 の nDCG@10 が、BM25 の 0.29 から 0.47 に上がった。検索語を約 40 個に増やすまでは効果が伸び、それ以上では下がった。
   - 現行の「クライアントが検索語を生成し、和集合を取る」設計は、この方向に合っている。欠けているのは、和集合の**順位付け**と、検索語の数の目安である。
2. **複数語の概念は語句として一致させるべきで、上位概念の自動追加は有害。**
   - TREC PM の比較実験（臨床試験コーパス。小規模で構造化されており、本件に近い）で、各要素を外したときの変化が報告されている。
     - 複数語を語句でなく単語の集まりとして扱う：−9.1%（抄録コーパスでは −15.5%）
     - 疾患の同義語展開を外す：−11.6%
     - 句ごとの重み付けを外す：−15.0%
     - **UMLS の上位概念を自動で加える：−12.4%**
   - 近接一致を語句単位に保つ v0.7 の修正と、上位概念を類縁概念フォールバックの内側に置く v0.5 の設計を、どちらも裏づける結果である。
3. **LLM が作る検索式は、実行ごとに再現率がばらつき、誤ったコードも混ざる。**
   - 系統的レビュー用の Boolean 検索式を ChatGPT に書かせた研究では、最良のプロンプトでも再現率 0.50（専門家の検索式は 0.83）だった。10 回の再実行での再現率のばらつきは平均の 12% あり、誤った MeSH 用語も多数生成された。
   - 生成し直した結果の和集合を取ること、コードを検証すること、ユーザーの元の語を必ず残すことが対策になる。
4. **LLM による関連性判定は、順位付けには使えるが、除外には使えない。**
   - GPT-4 による段階的スクリーニングの感度は 0.81〜0.96 だった。
   - 較正しないゼロショット判定では、再現率が 0.12 まで落ちた例がある。
   - 「判断できないものは除外しない」「除外には根拠となる引用を付ける」という条件付きで、候補の順位付けと絞り込みの補助に使う。
5. **よく調整した語彙ベースの検索は、小規模で構造化されたコーパスでは最先端に近い。**
   - TREC PM 2019 の臨床試験タスクでは、2 位が調整済みの BM25 だった。
   - MedCPT（医学向けの埋め込みと再順位付け）の BM25 に対する向上は nDCG@10 で約 +0.05 で、埋め込み検索単独では BM25 を下回った。
   - 埋め込みを採用しない判断による損失は限定的で、検索語の生成と統合で大部分を補える。
6. **系統的レビューでは、アウトカムで検索しないのが原則。**
   - Cochrane は、アウトカムは索引付けが弱く、題名や抄録に載らないことが多いとしている。
   - 本カタログでも Outcomes 欄の 19% が空で、アウトカムだけで絞る検索は、再現率に構造的な上限がある。
7. **Anthropic の Contextual Retrieval**（チャンクに文脈を前置きしてから索引化する手法）では、BM25 側だけでも検索失敗率が下がった。
   - 埋め込みのみ 5.7%、文脈付き埋め込み 3.7%、文脈付き BM25 を併用 2.9%。
   - PDF の節テキストに章見出しの階層を前置きする方法は、LLM を使わずにこの一部を取り込める。

## 選択肢と比較

| 手法 | 採否 | 理由 |
|---|---|---|
| LLM による検索語生成（概念ブロック別、ICD-10 の名称・包含用語・言い換え・略語・単複・カタログの書きぶり） | **採用** | 発見 1・3。現行の設計を拡張する |
| 和集合の重み付き RRF による順位付け（件数は切り詰めない） | **採用** | 発見 1。候補一覧を関連が高い順に出せる。暗黙の上位 N 件での打ち切りはしない |
| 検索語ごと・列ごとのヒット数と一致箇所の提示 | **採用** | 1,212 件問題のような「1 つの語が候補を膨らませる」事態を見えるようにする。パッセージランキングの考え方に相当 |
| 上位ヒットの抜粋を LLM が読み、漏れた言い回しを 1 回だけ補う | **採用** | 自動の擬似適合フィードバック（上位文書から語を機械的に足す）は話題のずれが起きやすい。LLM が読む方式なら避けられる。回数は 1 回に限り、由来を記録する |
| 検索語とコードの検証、ユーザーの元の語と広い種語の保持 | **採用** | 発見 3 |
| 段階的な LLM 関連性判定（カタログのメタデータだけで判定。満たす／満たさない＋引用／不明＝残す） | **採用** | 発見 4。一次判定上限を超えたときだけ使い、順位付けと絞り込み対話の補助にする |
| 下位概念の自動追加（ICD-10 の子コード） | **採用** | PubMed の explode と同じ考え方で、再現率に安全 |
| 上位概念の自動追加 | **不採用** | 発見 2。類縁概念フォールバックに限る |
| PDF の節への見出し前置き | **採用（低優先）** | 発見 7 |
| 評価用の正解集合（20〜30 問、複数の検索戦略の結果を合わせて作る） | **最優先** | 以降の変更の効果を測る前提になる |
| BM25 の列ごとの重みの調整 | 正解集合ができてから | FTS5 の `bm25()` は k1・b を変えられない（1.2／0.75 に固定。要確認）。列の重みだけ調整できる |
| 語幹の揃え（porter tokenizer） | 保留 | 当面はクライアントが単数形と複数形を両方出す |
| 埋め込み検索、SPLADE、cross-encoder、MedCPT、SapBERT | **不採用（制約）** | 失うもの：言い換えへの頑健さ。向上幅は約 +0.05 nDCG で、制御性が下がる。制約が緩めば最有力なのは SPLADE |
| doc2query（研究ごとの言い換えを生成して索引に加える） | 見送り | サーバー側の LLM と派生索引が必要になる |

## 結論・推奨

段階構成を次のように定める。

1. **計画（呼出元 LLM）**：質問を概念ブロック（対象・アウトカム・曝露）に分ける。ブロックごとに、ICD-10 に基づく語群（名称、包含用語、言い換え、略語、単数と複数、カタログでの書きぶり）を作る。ユーザーの元の語と広い種語を必ず含める。コードは検証する。
2. **一次検索（サーバー、再現率重視）**：語句単位の近接一致で和集合を取る。検索語ごと・列ごとのヒット数を返す。Outcomes が空の研究は、アウトカム検索で見落とされる可能性として別に示す。LLM による言い回しの補完を 1 回だけ行う。
3. **順位付けと絞り込み（適合率）**：重み付き RRF で並べる。一次判定上限を超えた場合は、呼出元 LLM がメタデータで段階的に判定し、facets と合わせて絞り込み対話に使う。除外はしない。
4. **PDF 段階**：現行どおり。節の見出しの前置きを追加する。

実装の順序は、**正解集合（評価）→ 検索語ごとの内訳の提示 → 概念ブロックと生成指示の拡張 → RRF による順位付け → LLM による 1 回の補完 → 段階的判定**とする。v0.2.1 は、長い検索語の修正（v0.7）だけをバグ修正として先にリリースする。検索ロジックの変更は、正解集合で効果を測りながら v0.3 系で行う。

## 未解決事項

- 正解集合の作り方：誰がラベルを付けるか、判定者 2 名の一致を一部で確認するか。
- 呼出元 LLM が 1 回で判定できる候補数（先行研究では 20 件単位）。本カタログのメタデータの長さで要確認。
- LLM による補完語を自動で採用するか、ユーザーの確認を挟むか。AGENTS.md の「黙って選ばない」原則からは、確認を挟む案が有力。
- MedDRA を有害事象アウトカムの軸にする場合のライセンス（`docs/research/202609270400_terminology_sources.md` を参照）。
- FTS5 の `bm25()` で k1・b が固定かどうかの確認。固定なら、独自の順位関数が必要かを判断する。
