## 結論

指摘 1（別のプロセスが古い読み方の解析を保存する）と指摘 2（H5N1 の検索に季節性ワクチンの名前を具体語として加える）は、どちらも実在する問題で、直す。
レビューの実装案のうち、整合性を DB のトランザクションで保証すること、医薬品名の関係を「同じ／広い／狭い／別」に分けること、省いた所属薬を応答で見せること、短い製品名の別名を作ることは妥当で、採る。
一方、次の 3 点は、目的に対して重すぎるか、正しい結び付きを壊すので、別の形にする。

| レビューの案 | 実装者の判断 | 理由 |
|---|---|---|
| 翻訳の版を整数の revision で管理する | 翻訳の内容のハッシュで照合する | 正しさに必要なのは「解析を作ったときの翻訳が、今の翻訳と同じか」だけである。A→B→A と戻した後に、A のときに始めた抽出を保存しても、その読み方は今の翻訳 A と一致する。revision はこれを古いとして捨てるが、捨てる理由が無い。B のときに始めた抽出はハッシュが違うので、ハッシュでも正しく拒否できる |
| revision の無い既存の解析は、すべて現在のキャッシュとして使わない | 英語の文書と翻訳の無い文書の解析は、そのまま使う | これらの読み方は「翻訳なし」で一定で、今の読み方と一致する。全件を再抽出させる理由が無い。翻訳のある文書だけ、照合で古いと分かれば再抽出する |
| 薬効群の所属を、出典付きの関係データ（レビュー済みのファイル）で補う | 今は作らず、省いた所属薬を応答で見せるだけにする | 実データで見つかっている例は fosaprepitant の 1 件だけで、それを挙げる研究は 0 件である。出典の確認、ライセンス、辞書の更新ごとの検証という保守の手間に見合わない。省いたことを見せれば、利用者は気付ける。該当する研究が現れたら、データを作る |
| 修飾の語を一律には許さず、同義関係を規則か出典付きの対応で確かめる（レビューの 2 の手順 5） | 今の単語の包含を保つ | PR #66 の評価で、完全一致に寄せると正しい組が 12 組外れることを確かめた。修飾の語による誤りは、今の索引では見つかっていない（H5N1 は番号の非対称が原因で、手順 3 で直る） |
| 配合剤の成分を一対一で対応させる（手順 6） | 今は入れない | 二方向の対応で足りない例が、実データに無い。EMA のワクチン名は成分の組を 1 つの文字列で持つので、一対一にしてもこの型は直らない（レビューも認めている） |

## 指摘 1：別のプロセスによる古い解析の保存

### 問題の評価

stdio の MCP サーバーは、クライアントごとに別のプロセスとして起動する。
Claude Code と Codex を同時に使うと、二つのプロセスが同じ利用者の DB と PDF の保存先を共有する。
したがって、レビューが再現した順序（B が古い翻訳で抽出を始め、A が翻訳を直し、B が古い解析を保存する）は現実に起こりうる。
PR #65 の取り消しは同じプロセスのタスクにしか効かないので、これを防げない。

### 実装

1. **翻訳の記録を SQLite に移す**：新しい表 `protocol_readings(protocol_id, reading, body)` に、言語、翻訳、parser の版を置く。`reading` は翻訳の内容をキー順に並べた JSON の SHA-256 で、翻訳の無い文書は空文字とする。今の `.headings` ファイルは、DB に記録が無いときに一度だけ取り込む（取り込みは `INSERT OR IGNORE` で、別のプロセスの記録を上書きしない）。以後の書き込みは DB だけにする。
2. **翻訳の変更と解析の失効を一つのトランザクションにする**：`BEGIN IMMEDIATE` の中で、今の翻訳と比べ、変わっていれば記録を書き換え、その PDF の解析を失効させる（履歴は残す）。
3. **解析の保存を条件付きにする**：解析の `source` に、抽出に使った読み方 `reading` を記録する。保存は `BEGIN IMMEDIATE` の中で、DB の今の `reading` と一致するときだけ行う。一致しなければ `READING_CONTEXT_CHANGED` を返す。照合と保存の間に別のプロセスが割り込めないので、確認してから保存するまでの隙間も無い。
4. **キャッシュの読み出しも照合する**：保存済みの解析の `reading`（記録が無ければ空文字）が今の読み方と違えば、キャッシュとして返さず、再抽出に回す。キャッシュの時刻の更新も条件付きの保存を通すので、失効した解析を書き戻さない。
5. **呼び出し側の抽出**：`analyze_protocol` のバッチの応答に `reading` を含め、`cache_protocol_analysis` に任意の引数 `reading` を加える。英語の文書では省略してよい。英語以外の文書では、渡された `reading` が今の読み方と一致しなければ、途中のバッチも含めて受け付けない。
6. **サーバー側の抽出**：タスクは抽出を始めたときの読み方で PDF を読み、その `reading` を付けて保存する。別のプロセスが翻訳を変えていれば、保存は拒否され、次の `analyze_protocol` で新しい読み方の抽出が始まる。

### テスト

- 同じ DB を共有する二つの `Service` で、レビューの順序（B が開始、A が翻訳を変更、B が保存）を固定し、B の保存が拒否され、旧解析が返らないこと。
- A→B→A で、A のときに始めた抽出が保存できること。B のときに始めた抽出が拒否されること。
- 呼び出し側が古い `reading` で保存すると拒否されること。英語の文書は `reading` を省略して今までどおり保存できること。
- `.headings` からの取り込みと、既存の解析（英語の文書）がそのままキャッシュとして使えること。

## 指摘 2：番号の無い広い名前を具体語にしない

`same_medicine` の真偽を、関係（`equivalent`、`broader`、`narrower`、`different`）を返す `medicine_relation` に置き換える。

- 単語の包含が成り立ち、番号の扱いが一致する（両方に無いか、両方にあって等しい）ときは `equivalent`。
- 一方にだけ番号があるときは、番号の無い側を広い名前とする。カタログの名前が広ければ `broader`、狭ければ `narrower`。
- それ以外は `different`。

`expand_medicine` での使い方：

| 関係 | 具体薬の検索でのカタログの名前 | クラスの所属薬 |
|---|---|---|
| `equivalent` | 検索語（`queries`） | 含める |
| `broader` | カテゴリー語（`category_terms`） | 含める |
| `narrower` | 加えない | 含める |
| `different` | 加えない | 含めず、`omitted_members` に名前、コード、カタログの名前、理由を載せる |

クラスの所属薬の判定は「そのコードのクラスに属するか」なので、名前が広いか狭いかは問わない。

## 指摘 3：省いた所属薬を見せる

クラスの検索で、名前の食い違いで省いた EMA の記録を `omitted_members` として `medicine_expansion` に載せる。
出典付きの関係データは作らない（理由は「結論」の表）。

## 短い製品名の別名

EMA の製品名の末尾にある `(previously ...)` だけを取り除いた名前を、同じ記録を指す追加の照合キーにする。
ほかの括弧は取り除かない（株、剤形、価数を消さないため）。
同じ別名が成分の組の異なる記録に当たるときは、その別名を使わない（黙って一つを選ばない）。
自由文の中での製品名の検出には使わない（今と同じく、名前全体の照合だけ）。

## 評価

- 指摘 2、3 と別名は、検索語の展開を変えるので、PR #66 と同じく、カタログと辞書の全名前で main と比べ、変わった展開を独立の判定者に判定させる。
- 短い製品名（Icandra、GoResp Digihaler、Vantavo）と H5N1 の具体名で、展開がどう変わるかを確かめる。
