# コードとデータを別々に版管理する実装計画

- 日付：2026-10-08（日本時間）
- 対象：v0.5.4 の次の版
- 位置づけ：[MCP再レビューと公開・更新方法の調査](202610081041_mcp_review_distribution_updates.md)の提案「コードとデータを別々に版管理する」を、公開は GitHub のままという前提で実装計画にしたもの。実装はまだしていない。

## 目的

カタログ DB（`data/ema.sqlite3`）は月に一度更新される。
今は DB をコードと同じリポジトリにコミットし、アプリの版を上げて配っている。
そのため、利用者が新しいカタログを使うには、MCP の設定の固定タグを書き換えて再起動する必要がある。
DB を月ごとのスナップショットとしてコードと別に配り、利用者のサーバーが自分で新しいスナップショットを取り込めるようにする。

## 前提と制約

- 公開は当面 GitHub のままとする（PyPI は保留）。利用者は `uvx --from git+https://...@vX.Y.Z` で起動する。
- 検索はローカルの SQLite だけで行う（AGENTS.md）。更新の確認は検索とは別の処理とし、検索の途中で通信しない。
- 通信先は GitHub だけで、EMA には触れない。EMA の CSV の取得は、保守者がブラウザで行う手作業のまま（robots.txt の制約）。
- 利用者の解析、質問別回答、保存した PDF、利用者が自分で取り込んだ CSV は、更新で失わない。
- 更新に失敗したら、今の DB のまま動き続け、失敗したことを状態に出す。

## 今の仕組み

- wheel は `data/ema.sqlite3` を同梱する。チェックアウトの外で初めて起動すると、利用者のデータフォルダへ複製する（`config.default_data_dir`）。
- 起動のたびに `storage.refresh_from_bundle(同梱DB, 利用者のDB)` が動く。同梱 DB の取り込み日時の方が新しければ、カタログの表だけを 1 回の書き込みトランザクションで置き換え、解析と回答の表には触れない。利用者が取り込んだ CSV の方が新しければ置き換えない。スキーマの版が違えば置き換えない。
- この関数は任意の DB ファイルを受け取れる。ダウンロードしたスナップショットをそのまま渡せるので、差し替えの部分は作り直さなくてよい。
- DB は 44 MB で、gzip で 17 MB になる。毎月コミットすると、Git の履歴が月に十数 MB ずつ増える。

## 選択肢と比較

### スナップショットの置き場所

| 置き場所 | 利点 | 欠点 |
|---|---|---|
| 同じリポジトリの GitHub Releases（タグ `data-YYYYMMDD`） | 費用なし。版ごとに不変の URL と添付ファイル。Git の履歴が増えない | アプリのリリースと同じ一覧に並ぶ（`--latest=false` で「最新版」表示から外す） |
| データ専用のリポジトリ | アプリと完全に分かれる | リポジトリが二つになり、権限と手順が増える |
| 今のまま DB をコミット | 仕組みの変更が要らない | 利用者の更新に設定の書き換えが要る。履歴が増え続ける |

推奨は、同じリポジトリの GitHub Releases である。

### 更新の起こし方

| 方式 | 利点 | 欠点 |
|---|---|---|
| 利用者が明示的に実行（CLI と MCP ツール） | 通信が予測できる | 利用者が忘れると古いまま |
| 起動時に確認だけし、状態で知らせる | 通信は小さい JSON だけ | 取り込みは利用者の操作待ち |
| 起動時に確認し、検証して自動で取り込む | 利用者は何もしなくてよい | 起動時に GitHub への通信が起きる |

推奨は、起動時に自動で取り込む方式を既定とし、環境変数で「確認だけ」と「しない」を選べるようにすることである。
「常に最新を使ってもらう」という目的には、利用者の操作を要しない方式が合う。
自動で取り込んでも安全に保てるのは、検証に通ったファイルだけを、今と同じトランザクションで差し替えるからである。

## 推奨設計

### 保守者の側（月に一度）

1. EMA の検索ページから、全研究と claims、ehr、registry の 4 つの CSV を同じ日にエクスポートする（今と同じ）。
2. 新しいスクリプト `scripts/build_catalogue_snapshot.py` が次を行う。
   - 4 つの CSV がそろっていて、ファイル名の日付が同じことを確かめる。
   - 空の DB に `import-all` で取り込み、前回のスナップショットから補完の結果（`merge-observations`）を移す。
   - `VACUUM`、`PRAGMA integrity_check`、件数（全研究と種別ごと）の確認、代表的な検索語での検索を行う。
   - gzip で圧縮し、SHA-256 を計算し、`manifest.json` を作る。
3. `gh release create data-YYYYMMDD --latest=false` で、圧縮した DB と `manifest.json` を添付して公開する。

`manifest.json` の中身：

| 項目 | 内容 |
|---|---|
| `snapshot_id` | `20261101` のような日付 |
| `schema_version` | DB のスキーマの版（今は 6） |
| `min_app_version` | このスナップショットを読めるアプリの最小の版 |
| `sha256`、`size` | 圧縮前と圧縮後の両方 |
| `exports` | 4 つの CSV のファイル名、行数、SHA-256 |
| `studies_total` | Non-interventional study の件数 |

### 利用者の側（サーバー）

1. 起動時に、検索の処理とは別のスレッドで確認する。前回の確認から 24 時間以内なら確認しない。
2. GitHub の API でリリースの一覧を取り、`data-` で始まる最新のタグの `manifest.json` を読む。
3. 次のどれかに当たれば取り込まない（理由を状態に記録する）。
   - 今の DB と同じか古いスナップショットである。
   - `schema_version` がアプリと違う、または `min_app_version` がアプリより新しい（アプリの更新が要る）。
   - 利用者が自分で取り込んだ CSV の方が新しい。
4. 一時ファイルへダウンロードし、SHA-256 と `integrity_check` で検証してから、`refresh_from_bundle` で差し替える。
5. 失敗したら今の DB のまま動く。オフラインのときも同じ。

設定は環境変数 `EMA_CATALOGUE_UPDATE` で選ぶ。`apply`（既定）、`check`（知らせるだけ）、`off` の三つとする。

### 状態の表示

`catalogue_status` に次を加える。

- `app_version`：動いているアプリの版
- `catalogue_snapshot`：今の DB のスナップショット ID と SHA-256
- `update`：最後に確認した日時、見つかった最新のスナップショット、取り込みの結果か失敗の理由
- `app_update_available`：GitHub に新しいアプリのリリース（`v` で始まるタグ）があれば、その版と、設定の固定タグを書き換える手順

アプリそのものの更新は、固定タグの書き換えと再起動が要るので、自動にはしない。知らせるだけとする。

### 研究の再現性

解析の `source` と比較表の JSON に、アプリの版、カタログのスナップショット ID、parser の版を記録する。
同じ質問の結果が月ごとに変わったとき、どの版の違いによるかを追えるようにするためである。

### 同梱 DB の扱い

wheel とリポジトリの `data/ema.sqlite3` は、オフラインでも最初の起動で検索できるように残す。
ただし更新はアプリのリリースのときだけにし、月ごとのコミットはやめる。

## 実装の段階

| 段階 | 内容 | 利用者への影響 |
|---|---|---|
| 1 | `manifest.json` の形式とスナップショット作成のスクリプト。最初のスナップショットを `data-YYYYMMDD` として公開する | なし（保守者の側だけ） |
| 2 | CLI `ema-rwe update-catalogue [--check]` と、`catalogue_status` の `catalogue_snapshot` と `update`。取り込みは利用者の明示的な実行だけ | 手動で更新できる |
| 3 | 起動時の自動確認と取り込み（`EMA_CATALOGUE_UPDATE`、既定は `apply`）。spec に通信の範囲を書く | 何もしなくても更新される |
| 4 | 解析と比較表への版の記録。月ごとの DB のコミットをやめ、リリース手順とドキュメントを改める | 結果に版が残る |
| 5 | アプリの新しい版の通知（`app_update_available`） | 設定の書き換えを促される |

各段階は単独でマージでき、前の段階だけでも役に立つ。
段階 3 は通信の振る舞いを変えるので、spec（新しい版）と `docs/validation.md` を同じ変更で更新する。

## 検証の計画

- 単体テストでは、GitHub の API と添付ファイルの取得を `httpx.MockTransport` で模擬する。
- 確かめる場合：新しいスナップショットの取り込み、SHA-256 の不一致、スキーマの不一致、`min_app_version` の不足、利用者の CSV の方が新しい場合、オフライン、ダウンロードの途中の失敗、2 つのプロセスが同時に起動した場合。
- 取り込みの後も、解析、質問別回答、保存した PDF の記録、補完した医薬品が残ることを確かめる（今の `refresh_from_bundle` のテストを流用する）。
- 実際の GitHub で、`data-` のリリースを 1 つ作り、uvx で起動した環境が取り込むことを確かめる。

## 未解決事項

- GitHub の API は、認証なしでは IP ごとに 1 時間 60 回まで。1 日 1 回の確認なら足りるが、同じ IP の利用者が多い組織では超えうる。超えたときは確認を翌日に回す。
- 社内のプロキシで GitHub に出られない環境では、自動の更新は働かない。状態に理由を出し、手動でファイルを渡す経路（`update-catalogue --file`）を用意するかを決める。
- EMA のカタログのデータを GitHub Releases で配ることの条件は、今リポジトリで配っているのと同じだが、NOTICE の記述がスナップショットにも及ぶことを明記する。
- アプリの固定タグを、`stable` のような動くタグに変えて自動で追従させる案は、uv が git の参照をどの程度キャッシュするかを確かめてから判断する。
