## 1. 調査目的

所有者の依頼は、次の 3 観点でのリファクタリングまたは全面的な再設計案である。

1. 処理速度：問い合わせから最終回答まで 3 分以内（プロトコルの選定、PDF 解析、LLM による回答の生成を含む）。
2. 正確性：各章（inclusion/exclusion criteria、study design、outcome definition など）の正確な抽出。既存研究が無い問いには、類似の疾患、薬剤、研究目的の組み合わせから案を推薦する機能。
3. 複数の提供形態：MCP を禁じる企業があるため、MCP、CLI、skills などを環境ごとに選べること。

本稿は、この 3 観点を同時に満たす構成と、そこへ至る工程を示す。

## 4. 主な発見

### 4.1 現状の時間の内訳

| 工程 | 値 | 区分と出典 |
|---|---|---|
| 検索語の計画（`plan_study_search` と呼出元の英語化） | LLM 1〜2 ターン | 未計測 |
| 候補選定（`compare_protocols` のうち PDF 取得前） | 0.07〜0.81 秒（4 ケース） | 実測（現状報告 2.2(b)） |

ここから 3 つのことが言える。

第一に、候補選定と PDF 解析は律速ではない。
候補選定はサブ秒で、解析は中央値 0.5 秒である。
企業のノート PC で 2〜3 倍遅いとしても（推計、未計測）、288 ページで 10〜15 秒にとどまる。

第二に、律速は呼出元 LLM の読解と PDF の取得の 2 つである。
読解は 1 研究 3〜5 分で、研究は直列に処理される（PDF 取得は全プロセス共通のロック、抽出は研究ごとに別のツール呼び出し）。
取得は記録上、研究ごとに 30 秒の間隔が要り、5 件で 2 分を超える。

第三に、研究ごとに並列化しても 3 分には届かない。
全体の所要時間が最も遅い 1 研究の 3〜5 分で決まり、そこに取得の 2 分が足されるからである。
したがって、問い合わせ時に PDF を読む設計のままでは 3 分を満たせない。

### 4.2 正確性の現状

- 逐語照合は「引用の文字列が PDF の該当物理ページにある」ことを保証している（`pdf.py:1095-1336`）。保証していないのは「抽出した値が引用の中の値と同じか」である（正確性報告 3）。
- 呼出元抽出の 1 回方式（抽出と同時に回答する）は、付録のコードや別章の値を落とす。アウトカム回答の「正しい」は 49324 で 7/9、105807 で 11/15（記録、validation.md v1.24）。
- スキーマの件数上限（answers 60、data_sources 60 など、`domain.py:164-192`）で項目が落ちうる。
- 表は PyMuPDF の平文化だけで、図は読まず、スキャン PDF は拒否する（442 件中 4 件、0.9%、実測）。
- 内部 LLM 経路の抽出精度は、正解データで採点していない（validation.md v1.20、v1.21 の限界）。
- 外部の知見で設計に効くのは次の 3 つである。
  - 長いプロトコルの抽出で、失敗した適格基準の 88.0% は転記の忠実度（比較演算子や数値の改変）だった（TrialPD-Bench、https://arxiv.org/abs/2610.18507 、2026-10-13 投稿、著者）。
  - 観察研究と系統的レビューの抽出で最も多い誤りは欠落だった（Gartlehner ほか、Ann Intern Med 2025-11-04、doi:10.7326/annals-25-00739、著者、抄録で確認）。
  - LLM にコードを提案させると、ICD の専門家一致は 20%、ATC は 50% だった（Ompad ほか、Clin Pharmacol Ther 2025-09-10、PMID 40929025、著者、抄録で確認）。決定的な検査器で micro-F1 は 0.254 から 0.505 に上がった（TrialCode Agent、https://www.medrxiv.org/content/10.64898/2026.08.20.26360962v1.full 、2026-08-23、著者）。

### 4.3 提供形態の現状

- 入口は stdio の MCP と argparse の CLI の 2 つで、同じ `Service` を呼ぶ。CLI だけで全工程を実行できるが、呼出元抽出では抽出 JSON を書く LLM エージェントが別に要る。
- 応答の中に、呼出元への自然言語の指示（`instruction`、`next_action`）がデータと混ざっている（`extraction.py:132-142`、`comparison.py:354-367`、`selection.py:171-179`）。ライブラリや JSON 出力として流用しにくい原因である。
- `_context` が取得、保存、来歴の計算を兼ねるため、HTTP キャッシュ（既定 30 日）が切れると、保存済み PDF があっても EMA へ再アクセスする。閉域では抽出できない。
- CLI は 1 呼び出し 1 プロセスなので、解析キャッシュ（プロセス内 8 件）が毎回失われる。
- 企業の多くは MCP を全面禁止より許可リスト制で扱う方向にある。Claude Code、Claude Desktop、GitHub Copilot、Cursor、Codex、Gemini CLI、ChatGPT は管理者向けの許可リストを公式機能として持つ（提供形態報告 1.2、各社の公式文書）。MCP を一律禁止した企業の件数を示す定量調査は見つからなかった（同報告、未確認）。
- MCP 2026-07-28 版で Roots、Sampling、Logging は非推奨候補になった（https://aaif.io/blog/mcp-2026-07-28-whats-changing-and-how-to-migrate 、2026-07-21、公式）。本サーバーはどれも使っていないので、この点の移行は要らない。

## 5. 目標アーキテクチャ

### 5.1 中心の判断

抽出を問い合わせ時から事前へ移す。
理由は 4.1 のとおりで、律速の 2 つ（読解と取得）はどちらも、問い合わせ時に行う限り並列化で 3 分に収まらない。
PDF 解析器の置き換え（Docling、Marker、MinerU など）は速度のためには採らない。
解析は律速ではなく、これらは CPU で 1 ページ数秒かかる（9 節）。

### 5.2 5 つの層

```
入口（層 5）   MCP / CLI(JSON) / Agent Skills / 静的成果物
      │  データだけを返す。手順の文章は docs/mcp-workflow.md と SKILL.md 側
回答の組み立て（層 4）  問い → 項目種別 → ストアから組み立て／足りない分だけ読解へ
      │
証拠ストア（層 3）  事実 1 件 = 1 行、FTS 付き。供給元は段 0／段 1／段 2
      │
文書ストア（層 2）  PDF（SHA-256）と解析済みページを永続化。取得と解析を抽出から分離
      │
カタログと検索（層 1）  現行の SQLite FTS5 と RRF の順位付け
```

**層 1（カタログと検索）**：現行のまま残す。
候補選定はサブ秒で、相対再現率 0.965（記録、validation.md 2026-09-28、暫定ラベル）を持つ。
変えるのは、層 3 の事実で研究を絞れるようになる点だけである（例：アウトカム定義に特定のコードを使う研究）。

**層 2（文書ストア）**：取得と解析を抽出から切り離す。

- 解析済みページ（`pages`、`sections`、しおり由来の読み順）を、PDF の SHA-256 と parser の版をキーにディスクへ永続化する。現行のプロセス内 8 件のキャッシュを置き換え、CLI でも 2 回目から解析しない。
- `_context` の結合を外す。取得（ネットワーク）と来歴の計算（fingerprint）を別の関数にし、アーカイブ済み PDF があればネットワーク無しで抽出と保存ができるようにする。fingerprint の成分と無効化の規則は変えない。
- 閉域向けに PDF の手動取り込み経路を設ける（CLI `import-pdf` 相当）。外で取得した PDF を研究 ID と共に渡し、SHA-256 を計算して保存する。最新版の選択理由は、カタログの Study documents の情報と照合できない場合は「手動取り込み、版の照合なし」と記録する。

**層 3（証拠ストア）**：質問に依存しない抽出結果を、研究ごとの JSON 1 塊ではなく事実 1 件 = 1 行で持ち、FTS をかける。

| 列 | 内容 |
|---|---|
| `pdf_sha256`、`study_id`、`protocol_id` | どの PDF の事実か |
| `item_kind` | 項目種別（`cohort.inclusion`、`cohort.exclusion`、`cohort.index_date`、`outcome.definition`、`exposure.definition`、`data_source`、`study_design` など。現行スキーマ 0.3 の項目から作る） |
| `value` | 正規化した値（コードは体系付き、期間は数値と単位） |
| `page`、`section_label` | 物理ページと章ラベル |
| `quote_start`、`quote_end`、`quote_sha256` | ページ本文の中の引用の位置と、正規化した引用文字列のハッシュ |
| `quote` | 逐語引用。手元で PDF から復元した後だけ埋まる（論点 2 の (a) の場合） |
| `role_tag` | A2 の役割判定（定義、除外、併存症、共変量、不明） |
| `usage` | データソースの planned、used、candidate、unclear（現行の区別を保つ） |
| `status` | `verified_local`（手元で逐語照合済み）、`verified_at_build`（配布元で照合済み、手元は未照合）、`absent_confirmed`（A3 の「記載なしを確認」）、`unchecked` |
| `tier`、`extractor`、`prompt_version`、`parser_version`、`app_version`、`snapshot` | 供給元（段 0、1、2）と来歴 |

この形にする理由は 3 つある。

1. 回答キャッシュが質問文字列の完全一致に依存しなくなる。現行の質問別回答の鍵は SHA-256（protocol_id、質問文字列、…）で、言い換えた質問は当たらない（`exploration.py:178-198`）。証拠ストアでは、問いを項目種別へ対応づけ、ストアから組み立てる。
2. PDF 由来の事実で研究を検索できる。カタログの列には無い「アウトカムを ICD-10 K85 で定義した研究」などを、FTS で引ける。
3. 推薦機能（5.6）が、問い合わせ時に PDF を読まずに成立する。

**層 4（回答の組み立て）**：ストアで答えられる問いは読解 0 回で答える。
答えられない自由文の問いだけ、関連節に限った読解（現行の `research_protocol` 相当）へ落とす。
この場合は 3 分を超えうる。
これを限界として明記し、応答にも「ストアに無いため PDF を読んだ」ことを示す。

**層 5（入口）**：薄いアダプタにする。

- 応答から指示文とデータを分ける。応答には機械可読な状態（`next_action` は列挙値、引数は構造化）だけを入れ、自然言語の手順は `docs/mcp-workflow.md` と、そこから派生する `SKILL.md` に置く。
- ツールは現行 18 個（要確認 12.2 の 1）から、ストア前提で 6 個前後へ減らす方向にする：計画、検索と比較、回答、推薦、状態、取り込み（カタログ CSV、スナップショット、PDF）。
- 段 2 の呼出元抽出（バッチを返し、引用付きの JSON を受け取る往復）を「回答」ツールの続きとして扱うか、抽出用のツールを 1 個残すかは、実装時に決める。どちらにしても、CLI と MCP の対応表テストに同じ変更を入れる。

### 5.3 証拠ストアの供給元

| 段 | 何か | 実行者と時期 | 方針変更 |
|---|---|---|---|
| 段 0 | 月次スナップショット `data-YYYYMMDD` に事前抽出を同梱する | 保守者。スナップショットのビルド時。強いモデルと検証パス（A5）を使える | 要（論点 1、2、3） |
| 段 1 | 利用者が手元で走らせる事前抽出。関心領域だけを夜間などに済ませる | 利用者。内部 LLM または呼出元エージェント | `backfill-protocols` と同じ位置づけ。例外の範囲を広げる文言の変更が要る（要確認 12.2 の 6） |
| 段 2 | 問い合わせ時の抽出（現行経路の改良） | 呼出元または内部 LLM | 不要 |

3 段の結果はすべて同じストアに入り、`tier` 列で区別する。
段 2 は方針変更なしで着手でき、段 0 が無い研究の受け皿として残る。

段 2 の改良は 4 つである（速度報告 5.2、8）。

1. 研究ごとの読解を、並列のサブエージェントへ同時に委譲するよう手順書に明記する。5 研究の合計 15〜25 分が、最長の 1 研究（3〜5 分）になる（推計）。
2. 取得の先読み：一次判定の上限以内の研究が決まった時点で、全研究の PDF の取得と解析を裏で始め、1 件目の読解と 2 件目以降の取得を重ねる。上限を超えるときは先読みしない（`AGENTS.md`）。ブリーフにある「絞り込み質問の裏での先読み」は、この規則と衝突しうる（要確認 12.2 の 3）。
3. `max_chars` を 12 万字へ寄せる。442 件の実測で、12 万字なら 9 割の研究が 1 バッチで済む（MCP 既定の 3 万字では中央値 2、p90 で 5 バッチ）。
4. 比較表など大きな結果は `resource_link` で返し、`content` には要約と件数とテキストの代替を置く。

### 5.4 配布物に入れるもの

EMA の再利用条件は、オーケストレーターが 2026-11-20 に次のとおり確認した（本稿の作成者は再確認していない）。

- EMA の legal notice（https://www.ema.europa.eu/en/about-us/about-website/legal-notice ）は EMA 自身の資料の再利用を出典明記で認める。ただし「The above-mentioned permissions do not apply to content supplied by third parties.」とする。
- カタログの legal notice（https://catalogues.ema.europa.eu/legal-notice ）は「Third parties may own copyright on the documents published on this site.」「Permission for their reproduction must be obtained from the relevant copyright holder/s.」とする。
- どちらも自動アクセスや TDM に触れていない。カタログの投稿規約は未確認である。

プロトコルは主に販売承認取得者や研究者が作った第三者の文書なので、本文の再配布（速度報告の案 A、解析済み本文の配布）は採らない。

推奨は、正規化した事実の値と位置情報（PDF の SHA-256、物理ページ、ページ内の文字範囲、章ラベル）だけを配り、逐語引用の文字列は配らないことである。
利用者の手元で PDF を取得した時点で、位置情報から引用を復元し、既存の逐語照合で検証する。
未取得の間は「引用は PDF 取得後に表示」と示す。

位置情報からの復元には、技術的な前提が 1 つある。
文字範囲はテキスト抽出器（PyMuPDF の版）と parser の版に依存するので、配布側と手元で版が違うと範囲がずれうる。
そこで、範囲と一緒に正規化した引用のハッシュと長さを配る。
手元では、まず範囲で切り出してハッシュを照合し、合わなければ同じページの中で同じ長さの窓をずらしてハッシュの一致を探す。
それでも見つからない事実は `status=verified_at_build` のまま残し、回答には「手元の PDF で引用を確認できなかった」と書く。

これは法的判断ではない。
最終判断は所有者に委ねる（論点 2）。

### 5.6 推薦機能

既存研究が無い問いへの推薦は、証拠ストアが前提になる。
推薦の部品（適格基準、index date、追跡、曝露とアウトカムの定義、コード、データソース）は、問い合わせ時に PDF を読まずにストアから集める必要があるからである。

正確性報告 11 節の B1〜B5 を採る。

| 施策 | 内容 |
|---|---|
| B1 軸ごとの部品検索 | 問いを疾患、薬剤、研究目的（安全性、有効性、薬剤使用、記述疫学）、デザイン、データソースの種類、国の軸に分け、軸ごとに最も近い研究を別々に示す。どの軸が一致し、どの軸が一致しないかを表にする |
| B2 出典付き部品の組み合わせに限る | 案の各要素は必ず（研究 ID、PDF の ID、物理ページ、逐語引用または位置情報）を持つ。出典の無い補完は「LLM による補完（根拠なし）」という別欄にしか書けない。コードは出典プロトコルに現れたものか、同梱辞書の存在検査を通ったものに限り、LLM にコードを生成させない |
| B3 決定的な整合性検査 | claims に検査値は無い、コード体系と国（ICD-10-GM、-CM、WHO 版）の混在、薬効群と成分、配合剤と単剤の取り違え、新規使用者デザインなのに washout が無い、追跡期間とデータソースの収録期間、計画と実際の使用の区別。まず 5〜10 規則から |
| B4 階層による類似度 | 薬剤は EMA 医薬品辞書の ATC コードの接頭辞の一致段数（名称表は同梱しない）。デザインとデータソースはカタログの構造化項目の一致。疾患は呼出元が渡す類縁語（ICD-10 を手がかりにする現行の `client_expansion` と同じ）。埋め込みは入れない（既存の設計制約を維持し、必要が実証されてから再検討） |
| B5 非類似点の明示と「前例なし」の明言 | 推薦の各研究について一致しない軸を列挙する。すべての軸で近い研究が無いときは「前例なし」と書く。確からしさは LLM の自己申告ではなく、一致した軸の数と出典付き要素の割合で示す |

現行の `analogous_fallback`（`screening.py:161-281`）との差分：

| 点 | 現行 | 再設計 |
|---|---|---|
| 発動 | 概念検索が 0 件のときだけ | 候補があってもプロトコルに定義が無い場合、軸の一部だけが一致する場合も対象 |
| ブロック数 | 1 ブロックのみ（2 つ以上は `not_available_for_blocks`） | 軸ごとに別々に検索し、組み合わせる |
| 疾患の類縁語 | 呼出元の提案に全面依存。サーバーは疾患の辞書を持たない | 同じ（辞書は同梱しない方針を維持）。ただし類縁語で見つけた研究の定義はストアの出典付き事実として示す |
| 返すもの | 類縁候補の研究一覧と件数。PDF は読まない | 研究一覧に加え、出典付きの部品、一致しない軸、整合性検査の違反 |

推薦の評価（正確性報告 11 節 B6）は工程表に作業項目として載せる。

## 10. 結論と推奨

1. 全面書き換えはせず、層 2（文書ストア）と層 3（証拠ストア）を足して、既存の `Service` と入口を段階的に載せ替える。
2. 3 分以内を満たす道は、抽出を問い合わせの前へ移すことだけである。目標は案 3（段 0＋1＋2）で、案 2 までを先に作る。
3. 正確性は、決定的な検査（A1、A2、A4、A7）と「記載なし」の構造化（A3）を先に入れ、LLM の呼び出しが増える検証パス（A5）は事前抽出に置く。
4. 推薦は証拠ストアの上に作り、出典付きの部品の組み合わせに限る。出典の無い補完は別欄に分け、コードを LLM に生成させず、決定的な整合性検査を通し、一致しない軸を示し、近い研究が無ければ「前例なし」と書く。
5. 提供形態は、MCP を審査用資料つきで残し、CLI の JSON 入出力と Agent Skills、静的成果物、CLI と社内 LLM、PyPI と出所証明、オフライン束を足す。
6. 工程は P1（段 2 の即効改善）と P2（提供形態の即効分）から始める。どちらも方針変更が要らず、単独で価値が出る。

- 抽出と索引を問い合わせの前に済ませる（外部報告 4 節。本稿 5.1 節）。

- 根拠が足りないときは答えない（外部報告 5 節。本稿 A3、B5）。

## 14. 判定モデルの扱い（2026-11-21）

### 14.1 対象と確認できたこと

`docs/research/20261121_deep-research-report-jev.md`（以下「判定モデル報告」）は、文章を生成せず、決められた選択肢への判断だけを返すモデルを、検索と回答の各段に挟む案である。
これも untrusted input として扱う。

2026-11-21 に Web 検索で確かめたこと（いずれも二次情報で、ベンダーの文書は読んでいない）：

- Jev は TypeSafe AI が 2026-09-15 に公開した判定モデルで、問いの型は Choice（選択肢から 1 つ、全選択肢の確率を返す）、Score（段階評価）、Noul（はい／いいえの確率）の 3 つである（https://www.datacamp.com/blog/system-one-models-jev 、https://www.braintrust.dev/articles/what-is-jev 、第三者）。
- OpenAI も 2026-09-29 に同種の Decisions API を発表した。一般提供の時期は記事の間で食い違う（https://thenewstack.io/openai-decision-models-deployment/ 、第三者）。
- 性能の数値はベンダーの発表で、学習の目的関数は公開されていないとする論文がある（https://arxiv.org/pdf/2610.02486 、著者、検索結果の要約経由）。

確かめていないこと：価格（100 万トークン 0.042 ドル）、版（jev-1.14.0）、画像への Box 問い、応答 70〜500 ミリ秒、分類の正確度。
報告の中の計算にも誤りがある。
「入力 1,000 トークン（0.042 ドル）」は、同じ報告の単価で計算すると 0.000042 ドルで、1,000 倍ずれている。
「Recall 90%（9 件中 8 件）」は 89% である。

### 14.2 前提の違い

判定モデル報告は、問い合わせのたびに候補の文書を LLM に読ませる構成を前提にしている。
費用の式（候補 N 件 × LLM の呼び出し）も、応答時間の議論もそこから出ている。

本稿の構成では、この前提がほぼ成り立たない。

- 問い合わせ時の読解は、ストアで答えられる問いでは 0 回である（5.2 節の層 4）。挟む先の LLM の呼び出しが無い。
- 候補選定は 1 秒未満で（4.1 節）、判定モデルで速くする余地が無い。
- 研究の候補を判定で落とすことは、「候補を黙って捨てない」（5.8 節）に反する。判定モデル報告も、見逃しを最大の危険として挙げている。

したがって、判定モデルが効きうる場所は問い合わせ時ではなく、事前抽出（段 0、段 1）と、自由文の問いの受け皿（R2）に限られる。

### 14.3 使いどころの候補

| 番号 | 場所 | 問いの型 | 現行案との関係 | 採否 |
|---|---|---|---|---|
| D1 | A2 コード言及の役割判定のうち、規則で決まらず「不明」に残ったもの | Choice（定義、除外、併存症、共変量、不明） | `role_tag` の値がそのまま選択肢になる。規則が先で、判定は残りだけ | 試す |
| D2 | A5 検証パス（値と引用のページを渡して支持するかを問う） | Choice（支持、不支持、欠落の疑い） | 新しいセッションの LLM の代わり。事実 1 件ごとの問いを 1 回の呼び出しにまとめられる | 試す |
| D3 | 段 0、段 1 で抽出器に渡す段落の絞り込み | Noul（この段落に項目 X の記載があるか） | 論点 3 の費用を下げうる。見逃すとその事実がストアから欠ける | 条件付き。落とさずに順序だけ変える使い方から始める |
| D4 | R2 で読ませる段落の並べ替え | Score | R1 の FTS の順位を補う | 保留。R1 で足りないと示されてから |
| D5 | A3「記載なしを確認」の判定 | Noul | 「無い」と言うには関連する章をすべて読む必要がある。判定モデル報告も同じ結論である | 採らない |
| D6 | 研究の候補の足切り、問いの意図の分類 | Noul、Choice | 14.2 節のとおり。意図の分類は呼出元 LLM が計画の 1 ターンで済ませている | 採らない |

判定モデル報告から、モデルの採否と無関係に取り入れる原則が 2 つある。

- 規則で決まるものは規則で決め、判定は残りだけに使う（同報告「見出しルール vs Decisionモデル」）。現行の章役割の判定（`pdf.py`）と同じ向きである。
- 確信が低いときは落とさずに通す（同報告「偽陰性リスクと対策」）。D1 では「不明」に残し、D3 では抽出器に渡す。

### 14.4 入れ方の制約

- 既定の経路には入れない。`AGENTS.md` は API キー不要の呼出元経路を既定に保つことを求めている。判定モデルは外部の有料 API で、プロトコルの本文を第三者へ送る。閉域では使えない。
- 内部 LLM と同じく、環境変数で設定したときだけ働く任意の部品にする。未設定なら D1 は「不明」のまま、D2 は現行の検証パス（または無し）で動き、スキーマは同じである。
- 特定のベンダーに結びつけない。D1 と D2 の出力は閉じた選択肢なので、規則、設定済みの内部 LLM（選択肢を制約した出力）、判定モデルのどれでも同じ列を埋められる。専用の抽象層は先に作らず、2 つ目の実装が要るときに切り出す。
- 判定の結果は来歴に残す。ストアの `extractor` 列に判定器の名前と版を入れ、判定器が変わったら該当の行を無効にする（5.8 節の来歴の規則と同じ）。
- 判定の確率を、事実の確からしさとして利用者に見せない（9 節「確信度の数値の表示」と同じ理由）。使うのは通すか残すかの内部の分岐だけである。

### 14.5 工程と論点への影響

- P4（A2）と P6（A5）の設計で、出力を閉じた選択肢にしておく。これは 5.5 節の案のままで、追加の作業は無い。
- 論点 3 で勧めた「10 研究での費用と時間の計測」に、D1 と D2 を判定モデルで行った場合の列を足す。採否はその結果で決める。測り方は正確性報告 8 節の枠組みに従う。
- 論点 6（新設）：事前抽出でプロトコルの本文を判定モデルの API（TypeSafe AI または OpenAI）へ送ってよいか。段 0 は保守者の判断、段 1 は利用者の設定による。推奨は「段 0 の計測でだけ試し、既定にはしない」。
- 14.1 節の未確認の項目（価格、入力長の上限、利用規約での入力データの扱い）は、計測の前にベンダーの文書で確かめる。

## 15. プロトコル間の関係の持ち方（2026-11-21、所有者の質問への回答）

問い：プロトコル間の類似性と章ごとの関連性を GraphRAG の形で持つほうが、未知の問い合わせに対応しやすいのではないか。

結論：関係は持つ。GraphRAG の処理系は採らない。
13.4 節の「知識グラフ、Graph-RAG を採らない」は、この節の意味に改める。

### 15.1 分けて考える 2 つのもの

| | GraphRAG の処理系 | 証拠ストアから導く関係 |
|---|---|---|
| 節と辺の作り方 | LLM が本文から実体と関係を抜き出す | 検証済みの事実の行から機械的に作る |
| 要約 | LLM がまとまりごとの要約文を書き、回答に使う | 作らない。件数と出典の一覧を返す |
| 出典 | 要約文は逐語引用を持たない | 辺の 1 本ずつが事実の行（物理ページと引用）に戻れる |
| 構築の費用 | 抽出とは別に、全文への LLM の呼び出しが要る | 追加の LLM の呼び出しは無い |
| 保存先 | グラフ DB または専用の索引 | 同じ SQLite の表と結合 |

証拠ストアの行は、すでに辺の一覧である（研究 —項目種別→ 値）。
同じ値を共有する研究は結合で引け、数段たどる問いは再帰の問い合わせで書ける。
約 2,150 研究の規模では、類似度を事前に計算して持つ必要もない。

### 15.2 足すもの

| 番号 | 内容 | 段階 |
|---|---|---|
| G1 | 実体の正規化の表：データソースの名前（表記ゆれを 1 つの ID へ）、コード（体系付き）、薬剤（ATC）。研究をまたぐ辺の質はここで決まる | P5 |
| G2 | 研究間の類似を、共有する実体の一覧つきで返す（「この 2 研究はデータソース X とアウトカムのコード Y を共有する」）。数値だけを返さない | P7（B1 の拡張） |
| G3 | 章の間の関係：文書内は A4 の相互参照を辺として残す。文書間は同じ項目種別の行どうしを並べる | P4、P5 |
| G4 | 数段たどる検索：薬剤 → 同じ ATC の段 → その研究 → そこで定義されたアウトカム → 同じアウトカムを別の疾患で定義した研究 | P7 |

### 15.3 グラフで埋まらないもの

未知の問いで足りなくなるのは、多くの場合プロトコルの外の知識である（2 つの疾患が病態として近い、2 つの薬剤の作用機序が近い、など）。
プロトコルから作ったグラフには、プロトコルに書かれた関係しか入らない。
この部分は、現行どおり呼出元が渡す類縁語と、ATC と ICD-10 の接頭辞で補う。

### 15.4 再検討の条件

- G1〜G4 で引けない問いの型が、実際の問い合わせで繰り返し現れたとき。
- 「この領域の研究全体の傾向」のような集約の問いに、R5 の件数の集計では足りないとき。

その場合も、要約文を回答の根拠にせず、要約から事実の行へ戻れる形に限る。
