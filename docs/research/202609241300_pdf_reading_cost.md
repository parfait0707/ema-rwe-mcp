# PDF 全読のコストと圧縮対策の提案

## 実測（2026-09-24 パイロット q1、呼出元抽出ルート）

| 指標 | A（現行） | B（スキーマ圧縮） |
|---|---|---|
| turn 数 | 98 | 113 |
| `analyze_protocol` 呼出 | 38 | 82（文脈圧縮後に全研究を再読） |
| コスト | $22.3 | $30.1 |
| 結果 | 利用制限で中断 | 利用制限で中断 |

原因は 3 つ。(1) 研究 19786 は PDF 242 頁・関連セクション 247（48.8 万字）で、
`cache_protocol_analysis` が `coverage_complete=true` を要求するため全読が必要。
(2) 1 バッチ約 1.2 万トークンを呼出元の文脈に積むため、後続の各呼出が既読分を
毎回キャッシュ読みし直す（q1 A の cache_read 397 万トークン）。読む量に対して二乗で効く。
(3) 文脈が自動圧縮されると保存前の抽出が消え、B では 6 研究を最初から再読した。

スキーマ圧縮（-29%、約 1,500 トークン）はこの規模の前では誤差であり、引数エラーも 0 件だった。

## 提案

### 1. 読むのはサーバー側の安価モデルに任せる（既存経路を有効化）

`service.analyze_protocol` は `configured(settings)` が真なら `llm.extract_with_provider` で
サーバー側抽出し、呼出元には完成した抽出（数 KB）だけを返す。この経路は実装済みで、
パイロットでは未設定だったため呼出元抽出に落ちていた。

- 設定: `LLM_BACKEND=litellm`、`LLM_MODEL=anthropic/claude-haiku-4-5`（200K 文脈、$1/$5 per 1M）
  または `anthropic/claude-sonnet-5`（1M 文脈、$2/$10）。鍵は利用者自身の環境変数。
- 概算: 6 研究の関連文字 95 万字 ≒ 24 万トークン。各バッチは 1 回しか読まないので
  Haiku で約 $0.4、Sonnet 5 で約 $0.8。呼出元抽出の $22〜30 に対して 1/30〜1/50。
- 呼出元は研究ごとに `analyze_protocol` 1 回で済み、文脈圧縮も起きない。

### 2. サーバー側抽出をツールタイムアウトに耐える形にする（小さな変更）

`.codex/config.toml` の `tool_timeout_sec=180` に対し、19786 は 45,000 字バッチで 11 回の
逐次呼出になり超過しうる。

- バッチを `asyncio.gather` で並列化（同時 4〜6）。
- 1M 文脈モデルではバッチ上限を 45,000 字から 150,000〜200,000 字へ（Haiku は 120,000 字程度）。
  バッチ数が減ると重複事実のマージも減る。
- バッチ結果を `analysis_history` 相当の表に (study_id, fingerprint, batch_index) で
  チェックポイント保存し、途中で切れても再開できるようにする。
- 180 秒を超えそうな場合はバックグラウンドで続行し `status: extracting, progress: k/n` を返す。
  呼出元は `analyze_protocol` を再呼出しして完成を待つ。

### 3. 呼出元抽出ルートの圧縮耐性（鍵なし利用者向けの保険）

- `cache_protocol_analysis` に `batch_offset` を追加してバッチ単位の部分保存を受け付け、
  サーバーが 2 と同じマージで束ねる。`coverage_complete` は全バッチ揃った時点でサーバーが判定する。
  → 圧縮後も既読バッチを再読しない。
- MCP `instructions` に 1 文追加: 「`needs_client_extraction` で、安価な下位エージェントを
  起動できるクライアントなら研究ごとに委譲せよ」。Claude Code では Haiku サブエージェントが
  読み、主文脈には結果だけが戻る。

### 4. 全読の方針

全読は維持する（appendix のコードリストが定義の根拠）。ただし読む主体を 1 → 2 → 3 の順で
安価側へ寄せる。`selection_coverage` の文言「Keyword/heading selected sections」は 19786 で
263 中 247 を返しており実態と合わないので、`relevant` 判定の緩さも併せて見直す。

## 実施順

1. 設定のみで 1 を有効化し、19786 を含む q1 を再実行してコストと抽出品質を実測（コード変更なし）。
2. 2 を実装（並列化・バッチ拡大・チェックポイント・進捗応答）。
3. 3 を実装。`.mcp.json.sample` と README に `LLM_MODEL` の推奨値を追記。
4. スキーマ圧縮は title 除去のみ採用し、積極版の A/B は 1〜3 の後に必要なら再開。
