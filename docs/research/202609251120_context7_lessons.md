# Context7 MCP の仕様調査と rwd-catalogue-mcp への適用

## 目的

Context7（Upstash）は数万ライブラリのドキュメントから、質問に必要な断片だけを LLM に返す MCP。
「大量文書 → 必要な情報だけを少ないトークンで」という点で本 MCP と同型なので、
コンテキスト消費の最小化・検索の高速化・抽出結果の提示の 3 観点で設計を比較し、取り込める要素を挙げる。

## Context7 の仕様（2026-09 時点、公開情報から）

| 観点 | Context7 |
|---|---|
| ツール面 | 2 ツールのみ（`resolve-library-id(query, libraryName)`、`query-docs(libraryId, query)`）。ツール定義は約 200 トークン |
| 前処理 | オフラインの 5 段パイプライン: parse（Markdown/MDX/RST/notebook を snippet に分割）→ enrich（LLM が「何を・いつ・なぜ使うか」のメタデータ付与）→ vectorize（3 種の埋め込み）→ rerank（5 指標の加重点: 想定質問 15 問への適合 80%、LLM 品質 5%、整形 5%、ノイズ除去 2.5%、導入手順 2.5%）→ cache（Redis 多段） |
| snippet 形式 | `TITLE / DESCRIPTION / SOURCE / LANGUAGE / CODE` の固定 5 項目、40 個のダッシュで区切った平文。JSON は選択式 |
| 応答量の制御 | クライアントは query とトークン予算を送るだけ。サーバーが再ランクして予算内に収める（最低保証 10,000 トークン）。ページングと `mode` は廃止し、サーバーが件数を決める |
| ID 解決 | `resolve-library-id` は候補ごとに trustScore（0-10）、totalSnippets、totalTokens、versions、lastUpdateDate を返し、呼出元が開かずに選べる |
| 版 | 質問中の版表記から自動選択 |
| 更新 | 10〜15 日ごとの巡回。commit hash / パッケージ版で差分検出 |
| 効果（再設計前後） | 質問あたりのコンテキスト 9.7k → 3.3k トークン（-65%）、遅延 24 → 15 秒、ツール呼出 3.95 → 2.96 回 |

再設計の要点は「絞り込みを LLM 側からサーバー側へ移す」こと。以前は LLM が何度も呼び直して自分で選別していた。

## 本 MCP の現状（q1 サーバー側抽出モードの実測）

呼出元に返ったツール結果は 36 件・602,081 字（約 15 万トークン）。内訳:

| ツール | 回数 | 合計字数 | 最大 1 件 |
|---|---|---|---|
| `search_protocol_text` | 7 | 202,779 | 42,990 |
| `analyze_protocol` | 11 | 195,089 | 50,562 |
| `compare_protocols` | 3 | 93,683 | 43,188 |
| `research_protocol` | 6 | 82,049 | 21,062 |
| その他 9 ツール | 9 | 28,481 | 9,046 |

サーバー側抽出にしても、抽出結果 JSON 全体（1 研究 3〜5 万字）と全文検索ヒット（1 回 4 万字）を
そのまま呼出元へ返しているため、Context7 が「再設計前」に抱えていた状態にある。
ツール定義（17 本、約 5 千トークン）は遅延ロードで常駐しないので、支配的なのは応答本文である。

## 取り込める要素と提案

### A. 応答をサーバーで絞る（最優先・小改修）

Context7 の「query 付きで呼び、サーバーが再ランクして予算内に返す」を各ツールに入れる。

- `analyze_protocol`: 既定では要約（状態、件数、`missing_information`、fingerprint）だけを返し、
  抽出本体は `fields=[...]` または `detail=full` の指定時のみ返す。比較表は `get_protocol_comparison`
  が既に集約するので、呼出元が抽出全文を受け取る必要はない。1 件 5 万字 → 数百字。
- `search_protocol_text`: `max_chars`/`budget` を受け、ヒットを質問との関連順に切り詰める
  （現在は上限 4 万字超のヒット群をそのまま返す）。
- `compare_protocols`: `needs_narrowing` の候補一覧・`pending_tools` を圧縮（研究 ID と 1 行要約のみ）。
- 想定効果: 呼出元コンテキスト 15 万 → 4〜5 万トークン。Context7 の -65% と同程度。

### B. 平文の「事実カード」形式（小改修）

Context7 の固定 5 項目・平文・区切り線の形式に倣い、抽出結果の提示形式に
`format=text` を追加する。1 事実 = `FACT / VALUE / SOURCE(page, section) / QUOTE` の平文。
JSON のキー分（実測で 47.5k 字中 11k 字、約 25%）が消え、LLM も人間も読みやすい。
検証・保存は従来どおり JSON で行い、提示だけを変える。

### C. 候補を開かずに選べる指標（小改修）

`resolve-library-id` の trustScore / totalSnippets に相当する列を `search_studies` の compact 行に足す:
PDF の有無、頁数、抽出済みか、質問回答キャッシュ数、カタログ由来のデータソース種別。
呼出元が PDF を開く前に一次判定対象を絞れる。現行の `candidates` に一部あるので拡張で済む。

### D. オフライン前処理と想定質問への事前採点（大改修・方針判断が必要）

Context7 の中核は「事前に snippet 化し、想定質問 15 問への適合度で採点しておく」ことにある。
本 MCP でも、抽出済みプロトコルの事実を「アウトカム定義／コホート定義／打ち切り／曝露定義／
共変量／ベースライン期間」など定型質問への適合度で事前採点しておけば、`research_protocol` の多くが
LLM 呼出なしの検索で済み、数分 → 数秒になる。q1〜q6 はまさにこの定型に当たる。

ただし全 3,312 研究の PDF を事前取得するのは AGENTS.md の「選択した研究の PDF だけを取得し、
無制限のサイトクロールはしない」に抵触する。現実的な形は次の 2 段階:
1. 過去の質問で取得済みの PDF（キャッシュが育つ）に限って事前採点を行う。
2. 全件を対象にするなら、利用者が明示的に起動する 1 回限りのレート制限付きジョブとして設計し、
   方針変更として記録する。抽出は Batch API（半額）と安価モデルで一括処理する。

### E. ツール面の縮小（中改修）

サーバー側抽出が既定になった今、呼出元に必要なのは「探す・絞る・比較を得る・追加質問する」の
4 操作で、`analyze_protocol` のページング系引数や `cache_protocol_*` は鍵なしモード専用になった。
Context7 のように 2〜4 ツールの façade を前面に出し、鍵なしモード用の低レベルツールは
`instructions` で案内する構成にすると、遅延ロードをしないクライアント（Codex）での常駐トークンも減る。

## 取り込まないもの

- 埋め込みベクトル検索: 対象は 3,312 研究の構造化カタログと選択済み PDF で、FTS5 + 同義語辞書で
  足りている。ベクトル化は D を採用する場合に再検討する。
- 巡回更新: カタログ更新は公式 CSV export をユーザーが行う設計を維持する。

## 実施順の推奨

A → B → C は互いに独立で各 1 日以内。D は方針決定後。E は D の後に検討する。

## 追記（2026-09-25）: 両モードを前提にした効果順

既定設定（`LLM_*` 未設定）はクライアント側フォールバック（Claude Code では Sonnet サブエージェントへ委譲）で、
サーバー側抽出は `LLM_*` 設定時のみ。q1 フォールバックのツール結果は 325 万字（約 81 万トークン、
`analyze_protocol` 47 回 123 万字、`search_protocol_text` 52 回 85 万字、`get_protocol_outline` 12 回 42 万字）。
`needs_client_extraction` の各バッチにはスキーマと指示文 約 8,200 字が毎回同梱され、19786 の 29 バッチで 24 万字。

| 順 | 施策 | 効くモード | 想定効果 | 規模 |
|---|---|---|---|---|
| 1 | `research_protocol` の鍵なし応答を、質問との関連順に並べた予算付きセクション束に変える | フォールバック | 検索・目次・読み取りの往復 100 回超 → 1〜2 回。150 万字 → 20 万字 | 中 |
| 2 | バッチ応答のスキーマ・指示文を `offset=0` のみに | フォールバック | 19786 で 24 万字減 | 小 |
| 3 | `max_chars` 上限 60,000 → 150,000、Sonnet 向けに 120,000 を案内 | フォールバック | 29 バッチ → 5 バッチ | 小 |
| 4 | `analyze_protocol` 要約既定化、`get_protocol_outline` の絞込、候補一覧の圧縮、検索の予算 | 両方 | サーバー側抽出モード 60 万字 → 20 万字 | 中 |
| 5 | 平文の事実カード形式 | 両方 | JSON キー分 約 25% | 小 |
| 6 | 開かずに選べる指標を `search_studies` 行へ | 両方 | 開く PDF の件数を削減 | 小 |
| 7 | オフライン事前採点 | 両方 | 定型質問を即答 | 大・方針判断 |
| 8 | ツール面の縮小 | 遅延ロードなしのクライアント | 常駐トークン | 中 |
