# v0.6.0 実装計画：証拠ストア（claims から）

- 作成：2026-11-21（JST）。ブランチ `feature/evidence-store-v060`。
- 仕様：[v1.31](../spec/v1.31.md)。設計：[再設計案](202611202312_redesign_proposal.md) 16 節の決定。
- 完了の判定：下の「完了の条件」がすべて観測で満たされたとき、版を 0.6.0 にしてリリースする。

## 調査目的

再設計案のうち、v0.6.0 に入れる範囲と順序を決め、各段階の確かめ方を定める。

## 前提と制約

- 所有者の決定（再設計案 16 節）：全件の事前取得を認める。配るのは値と位置だけ。claims から始める。3 分はストアで答えられる問いに限る。静的ページは手元生成だけ。判定モデルは既定にしない。
- この環境には LLM の API キーが無い。サーバー側の抽出は動かせないので、試行の抽出は既存の呼出元経路（Claude Code のサブエージェントが読む）で行う。
- claims でプロトコルがある研究は 560 件（手元のカタログ、2026-11-21 に数えた）。正解データの 4 研究（49276、49285、49324、105807）はすべて claims に入る。

## 主な発見（設計を変えたもの）

1. 事実の行は、既存の解析 JSON（スキーマ 0.3）から機械的に導ける。新しい抽出処理も、解析と同期させる別の表も要らない。解析が消えれば行も消えるので、「reading の変更と解析の破棄は同一トランザクション」の不変条件をそのまま守れる。
2. 560 研究 × 1 研究あたり数十〜百数十件の事実なら、読むたびに導いて Python で絞っても 1 秒未満に収まる見込みである（推計。P3 で測る）。FTS の表は、測って遅いと分かってから足す。
3. 配る事実だけは解析を持たない利用者へ届くので、表（`prebuilt_facts`）が要る。カタログの表として扱えば、既存のスナップショットの検証と置き換えに乗る。

## 選択肢と比較

| 案 | 内容 | 採否 |
|---|---|---|
| 事実の表を解析と別に持ち、保存のたびに書く | 再設計案 5.2 節の形 | 採らない。解析を消す箇所が 5 か所あり、同期を外すと古い事実が残る |
| 事実を解析から読むたびに導く | 表を持たない | 採る（手元の事実） |
| 配る事実を解析 JSON（引用抜き）で配る | 形が 1 つで済む | 採らない。引用の位置とハッシュの列が要り、行の形のほうが単純 |

## 段階

各段階は単独でテストが通り、次の段階の前に確かめる。

| 段階 | 成果 | 確かめ方 |
|---|---|---|
| P1 | 仕様 v1.31 と本計画 | 所有者の確認 |
| P2 | `evidence.py`：解析から事実の行を導く関数、引用の位置とハッシュ、復元 | 単体テスト（全項目種別が行になる、planned と used が保たれる、位置から復元した引用が元と一致する、版がずれても窓探索で見つかる） |
| P3 | `find_facts`（MCP）と `facts`（CLI）、対応表テスト、手順書 | 対応表テスト、実 stdio の MCP テスト、560 研究規模の合成データでの応答時間 |
| P4 | `prebuilt_facts` 表（スキーマ 7）、`export-facts`、スナップショットへの同梱と置き換え、手元の解析の優先、復元 | スナップショットの作成、検証、置き換えのテスト。復元の成功と失敗の両方 |
| P5 | `prefetch-protocols`：claims、再開、429 の方針 | 429 を返す偽の HTTP で、1 分の間隔、15 分の休止、再開を確かめる（時間は差し替える） |
| P6 | `facts-site`：手元の静的 HTML | 生成した HTML に外部の資源が無く、事実と出典が並ぶこと |
| P7 | 試行：claims の PDF を事前取得（バックグラウンド、長時間）。10 研究（正解データの 4 研究を含む）を呼出元経路で抽出し、`find_facts` で答える | 下の「完了の条件」 |
| P8 | `docs/validation.md`、`AGENTS.md`、`docs/mcp-workflow.md`、`README` の更新、`release-consistency-audit`、版 0.6.0 | `uv run scripts/check.py` が通る |

## 完了の条件

1. `uv run scripts/check.py` が通る（gold の手順を含む）。
2. 試行の 10 研究について、`find_facts` が手元の事実を返し、引用がすべて逐語照合を通っている。
3. ストアで答えられる問い（例：ある研究群のアウトカム定義とコード）の 1 問全体が 3 分以内であることを、計測して `docs/validation.md` に記録する。
4. 試行の抽出の正確さを、正解データの 4 研究で採点して記録する（`scripts/extraction_eval.py`）。
5. `export-facts` で作った配布の事実を別のデータベースへ入れ、PDF がある研究は `verified_local`、無い研究は `verified_at_build` で返ることを確かめる。

## v0.6.0 に入れないもの

再設計案の A1〜A8（正確性の検査）、推薦（B1〜B7）、ツールの整理（6 個前後への削減）、段落索引（R1、R2）、判定モデル（D1〜D6）、他の source type、静的ページの公開。いずれも v0.6.0 の試行の結果を見てから順番を決める。

## 未解決事項

- 560 研究の全件抽出の費用と実行者。試行の 10 研究で 1 研究あたりのトークン数と時間を測ってから決める（論点 3）。
- 事前取得の所要時間。研究間 60 秒なら 560 研究で 10 時間前後になる（推計）。429 の頻度で延びる。
